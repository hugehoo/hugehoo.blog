buzzscreen-api의 PR에는 Go 코드를 검사하는 단계가 두 개 있다. 먼저 `recovergoroutine`이 새로 띄운 고루틴 안에서 panic을 복구하는지 확인한다. 이어서 `lint-buzzscreen`이 같은 코드에 `golangci-lint`를 돌린다. 첫 번째 검사기를 최적화한 뒤 PR 기록을 열어 봤다.

| CI에서 측정한 시간 | v0.5.0 | v0.5.1 |
| --- | ---: | ---: |
| recovergoroutine 설치와 실행 | 7분 24초 | 1분 54초 |
| lint-buzzscreen | 37초 | 4분 14초 |
| ci-lint 작업 전체 | 8분 34초 | 6분 43초 |

첫 단계에서 5분 30초를 줄였는데 내가 PR에서 기다리는 시간은 1분 51초 줄었다. 오히려 두 번째 단계가 3분 37초 길어졌다. 두 실행의 Go 소스는 같았지만, 첫 실행에서 재사용한 `golangci-lint` 분석 결과를 두 번째 실행에서는 재사용하지 못했다. 이 기록 한 쌍만으로는 검사기를 바꾼 영향이 얼마인지 알기 어려웠다. [변경 전 CI](https://github.com/Buzzvil/buzzscreen-api/actions/runs/43412381717/job/131841725919) · [변경 후 CI](https://github.com/Buzzvil/buzzscreen-api/actions/runs/43461393904/job/132008935107)

## 고루틴 하나를 검사하는 데 어디까지 읽어야 할까?

검사기가 찾는 건 `go func() { ... }()` 같은 코드다. 함수 안에 `defer`로 복구 함수를 등록했는지, 프로젝트에서 허용한 `Recover` 같은 이름을 썼는지는 Go의 구문 트리(AST)에 드러난다. 그런데 기존 실행 경로는 이 규칙을 적용하기 전에 패키지의 타입을 검사하고, 다른 패키지가 그 타입 정보를 읽을 수 있도록 준비하는 비용까지 냈다.

v0.5.1에서는 CLI를 일반적인 방식으로 실행할 때 빌드 조건과 테스트 파일을 반영해 패키지의 구문을 읽고 곧바로 검사한다. 이 경로에서는 타입 오류만 있는 코드가 통과할 수 있다. CI에서는 빌드나 `go test`가 그런 오류를 잡는다. [recovergoroutine 변경 내역](https://github.com/Buzzvil/recovergoroutine/pull/39)

같은 커밋의 503개 패키지, 테스트를 포함한 Go 파일 2,964개에 아래 명령을 실행했다.

```bash
recovergoroutine -recover=Recover ./components/buzzscreen/...
```

| 로컬 실행 조건 | v0.5.0 | v0.5.1 |
| --- | ---: | ---: |
| 빈 Go 빌드 캐시에서 시작, 버전당 1회 | 55.13초 | 7.30초 |
| 캐시를 채운 뒤 버전을 번갈아 3회씩 실행한 중앙값 | 2.60초 | 1.75초 |

Mac arm64와 Go 1.27.3에서 설치 시간을 제외하고 쟀다. 모듈 다운로드 캐시는 공유했다. 원본 코드는 두 버전 모두 통과했고, 복구 처리를 빠뜨린 고루틴 두 개를 넣자 진단 메시지와 종료 코드(`3`)도 같았다. 이 코드에서 검사기만 실행하면 빈 캐시에서 약 87%, 이미 채운 캐시에서도 약 33% 빨라졌다. [측정에 사용한 커밋](https://github.com/Buzzvil/buzzscreen-api/commit/5d7f84b06a98807c8b26a26676feb7abd142294d)

## 다음 린터가 기다린 것은 무엇이었나

두 검사기가 함께 쓸 수 있는 **Go 빌드 캐시**에는 컴파일 산출물과 패키지의 타입 정보가 들어간다. 이와 별개로 **golangci-lint 결과 캐시**는 이미 수행한 린트 분석을 재사용한다. 처음 본 PR 기록에서는 이 두 효과가 섞여 있었다.

이번에는 실제 Linux 러너 네 대에서 같은 Go 소스로 버전당 두 번씩 실행했다. 네 작업 모두 러너 이미지에 담긴 Go 빌드 캐시에서 출발했고, `golangci-lint` 결과 캐시는 비웠다. 도구 설치 시간도 측정에서 뺐다. [러너 비교 실험](https://github.com/Buzzvil/buzzscreen-api/actions/runs/43545051509)

| 측정 구간 | v0.5.0 | v0.5.1 |
| --- | ---: | ---: |
| recovergoroutine | 8분 07초~8분 10초 | 38초 |
| lint-buzzscreen 전체 | 2분 22초~2분 24초 | 10분 00초~10분 01초 |
| ↳ 그중 패키지 로딩 | 7.34~7.54초 | 7분 53초~7분 55초 |
| ↳ 그중 린트 규칙 실행 | 2분 10초~2분 12초 | 2분 00초~2분 03초 |
| 두 단계 합계 | 10분 31초~10분 32초 | 10분 38초~10분 39초 |

이전에도 두 도구는 각각 패키지를 읽었다. 다만 v0.5.0이 타입 검사에 필요한 산출물을 먼저 만들어 둔 덕에, 뒤의 린터는 패키지 로딩을 약 7초에 끝냈다. v0.5.1은 구문 검사만 하고 38초 만에 끝난다. 그러자 뒤의 린터가 필요한 타입 정보를 준비하느라 거의 8분을 썼다. 린트 규칙 자체를 실행한 시간은 양쪽 모두 2분 안팎이었다.

두 단계의 합계는 새 버전에서 평균 7초 길었다. 버전당 두 번이므로 7초를 성능 회귀로 단정하기는 어렵다. 다만 빈 린트 결과 캐시에서 첫 단계가 아낀 7분 30초를 CI 전체의 절감 시간으로 셀 수 없다는 점은 분명했다.

## 매번 내던 설치 비용은 러너 이미지로 옮겼다

타입 정보와 별개로 줄일 수 있는 시간이 하나 있었다. 러너 이미지에는 이미 `recovergoroutine` v0.4.0이 있었는데, buzzscreen-api는 원하는 버전을 맞추려고 CI 때마다 `go install`을 호출했다. 그래서 이미지의 바이너리를 v0.5.1로 올리고, CI에서는 `go version -m`으로 바이너리의 모듈 경로와 버전을 확인하게 했다. 둘 다 일치하면 바로 실행하고, 없거나 다르면 지정한 버전을 설치한다. [러너 이미지 변경](https://github.com/Buzzvil/docker-images/pull/248) · [buzzscreen-api 변경](https://github.com/Buzzvil/buzzscreen-api/pull/8497)

실제 러너에서 기존 버전을 v0.5.1로 처음 바꾸는 설치는 중앙값 **20.697초**(3회)였다. 같은 버전을 설치한 직후 다시 `go install`을 호출하면 **0.601초**(6회), 버전만 확인하면 **0.0205초**(6회)였다. 이미지에 미리 넣어서 아끼는 시간은 러너의 시작 상태에 따라 달랐다. 이 실험은 설치 구간만 쟀으므로 첫 표의 전체 CI 단축 시간에 20초를 더하지 않았다. [설치 비교 실험](https://github.com/Buzzvil/buzzscreen-api/actions/runs/43540599961)

## 타입 정보도 이미지에 미리 넣어 두면 어떨까?

기존 러너 이미지에도 Go 빌드 캐시가 약 4.31GB 있었다. 이미지를 만들 때 `/tmp/src`에서 빌드와 커버리지 테스트를 실행한 흔적이다. 그렇다면 린터가 필요로 하는 패키지와 테스트의 타입 정보를, 실제 CI가 코드를 체크아웃하는 경로에서 준비하면 얼마나 재사용할 수 있을까?

러너 여섯 대에서 같은 커밋을 대상으로 세 조건을 두 번씩 실행했다. 기존 이미지 캐시를 그대로 쓰거나, 임시 경로 또는 실제 체크아웃 경로에서 아래 명령으로 캐시를 먼저 채웠다. 여섯 번 모두 `golangci-lint` 결과 캐시는 비웠다. [Go 빌드 캐시 비교 실험](https://github.com/Buzzvil/buzzscreen-api/actions/runs/43546792127)

```bash
# 각 실험의 소스 경로 아래 components/buzzscreen에서 실행
go list -deps -test -export -compiled -buildvcs=false -pgo=off ./... >/dev/null
```

| 캐시를 준비한 조건 | 패키지 로딩 실측 (2회) | CI 작업 시간 추정 (같은 순서) |
| --- | --- | --- |
| 기존 이미지 그대로 | 2분 37초 / 11분 29초 | 4분 38초 / 15분 27초 |
| 임시 경로에서 추가 준비 | 3분 13초 / 1분 00초 | 6분 01초 / 2분 45초 |
| 실제 체크아웃 경로에서 추가 준비 | **9.3초 / 5.2초** | 5분 08초 / 1분 53초 |

실제 체크아웃 경로에서 캐시를 준비하자 패키지 로딩은 두 번 모두 10초 안에 끝났다. 표의 마지막 열은 실험 작업에서 캐시 준비와 진단에 쓴 시간을 뺀 추정치다. 기존 조건과 실제 경로 조건의 평균은 각각 10분 03초와 3분 31초였지만, 첫 실행끼리 보면 오히려 실제 경로 쪽이 30초 길었다. 러너 두 대씩의 평균 차이인 6분 32초를 모든 PR에서 아낄 시간으로 보기는 이르다.

비용도 있다. 실제 경로에서 캐시를 채우는 데 3분 10초와 14분 43초가 걸렸고, 디스크의 Go 빌드 캐시는 약 4.31GB에서 7.22GB로 늘었다(원본 바이트 기준 약 **2.92GB 증가**). 레지스트리에서 받을 압축 이미지의 증가분이나 새 러너가 이미지를 받는 시간은 아직 재지 않았다. 새 라이브러리가 추가되면 Go는 필요한 모듈을 내려받고 영향을 받은 패키지를 다시 빌드한다. 기존 캐시에서 입력이 같은 패키지는 계속 재사용할 수 있다.

이번에 적용한 변경은 검사기 최적화, buzzscreen-api의 버전 갱신, 러너에 미리 설치한 바이너리 재사용까지다. 빌드 캐시 사전 준비는 실제 러너에서 가설을 시험한 단계다. 처음에는 38초가 된 고루틴 검사에 눈이 갔다. 지금 다시 CI 기록을 연다면 바로 다음 줄의 패키지 로딩 시간부터 같이 볼 것 같다.
