## 메모리는 줄었는데 GC 그래프는 올라갔다

운영 중인 Go 서버에서 메모리가 줄었는데 GC는 오히려 늘었다. 메모리를 덜 쓰면 GC도 할 일이 줄어들 것 같은데, 그래프는 반대로 움직였다.

![Go 메모리 사용량이 급감하는 시점에 초당 GC 횟수가 증가한 Datadog 그래프](go-memory-and-gc.png)

_위는 Go 메모리 사용량, 아래는 GC 빈도의 추이다. 메모리가 내려가는 구간에서 GC 빈도는 올라간다. 그림은 며칠간의 흐름이고, 아래 표는 그중 전후 30분씩을 비교한 값이다. 그림의 Heap Total과 표의 생존 heap은 다른 지표다._

변화 전후 각각 30분의 Datadog 지표를 비교했다. (MiB는 메모리 크기 단위로, 1 MiB는 1,048,576바이트다.)

| 지표 | 이전 | 이후 |
| --- | ---: | ---: |
| 생존 heap | 75.63 MiB | 48.89 MiB |
| 평균 heap 할당률 | 238.02 MiB/s | 239.87 MiB/s |
| 평균 GC 빈도 | 3.68회/초 | 6.01회/초 |


생존 heap은 약 35% 줄고 GC 빈도는 약 63% 늘었다. 반면 새 객체를 저장하기 위해 heap에 할당한 메모리는 초당 약 238 MiB에서 240 MiB로 거의 같았다. 표의 ‘평균 heap 할당률’이 이 값이다.

예를 들어 요청을 처리하며 JSON을 읽어 객체를 만들면, 그 객체를 저장할 공간이 필요하다. 할당률은 이렇게 새 객체에 할당한 공간을 초당 합산한 값이다. 금방 사용을 마친 객체도 포함하므로, 초당 240 MiB를 할당한다고 사용 중인 메모리가 매초 240 MiB씩 쌓이는 것은 아니다.

## 새 객체에 할당하는 메모리와 GC 후에도 사용 중인 메모리

heap은 프로그램에서 동적으로 할당한 객체를 두는 메모리 공간이다. 모든 Go 변수가 heap에 할당되는 것은 아니지만 여기서는 heap에 할당한 데이터와 캐시에 집중하자.

참조는 프로그램이 객체를 가리키는 연결을 의미하는데, GC는 이 연결을 따라가 도달할 수 있는 객체를 찾고 더 이상 도달할 수 없는 객체의 공간을 회수한다. 프로그램이 계속 붙잡고 있는 객체는 임의로 버리지는 않는다.

**할당률은 새 객체에 초당 할당한 메모리 크기이고, live heap은 직전 GC에서 아직 참조 중이라고 판단한 객체들의 메모리 크기다.**
임시 객체도 GC 시점에 참조 중이라면 live heap에 포함될 수 있다.

> 참고로 live heap이란, 가비지 컬렉션이 끝난 후에도 살아남은 실제 객체들의 메모리 크기로 만약 이 수치가 계속 증가하면 memory leak을 의심해 봐야 한다.

객체를 더 이상 사용하지 않아도 GC가 처리하기 전까지는 메모리 공간을 차지할 수 있다. GC 이후에는 해당 공간에 다른 객체를 저장할 수 있지만, Go Runtime이 이 빈 메모리 공간을 다음에 쓰려고 보관하기도 한다. 그렇기 때문에 GC가 끝났다고 운영체제에서 보는 메모리 사용량이 바로 줄어들진 않는다.이번 조사에서는 전체 Go 메모리 감소와 별개로, 생존 heap 자체가 줄어든 것을 확인했다.

## 대량 캐시 삭제가 있었다.

메모리 감소가 발생했던 날의 배포 이력을 살펴보니 광고 설정을 벌크로 수정하는 PR이 있었다.
팀원에게 확인해본 결과 실제로 대량의 광고 오프 작업이 수행됐고, 작업의 결과로 메모리 감소까지 이어진 걸 확인했다.

![광고 항목의 대량 비활성화 여부를 묻고 팀원이 약 14만 건을 처리했다고 답한 Slack 대화](bulk-deactivation-slack.png)

_여기서 14만 건은 비활성화한 광고 항목 수로 로컬 캐시에서 삭제된 항목 수와 정확히 일치하는 것은 아니다._

그렇다면 광고 항목을 비활성화한 것이 서버 메모리 감소로 어떻게 이어졌을까?
Pyroscope의 메모리 프로파일을 비교해, 어느 코드에서 할당한 메모리가 줄었는지 확인했다.

살아 있는 객체의 메모리를 보는 `inuse_space`에서 감소가 집중된 곳은 광고 JSON을 로컬 캐시에 넣는 지점이었다.
이곳의 표본 합은 약 72% 줄었고 나머지는 거의 같았다.

비활성화된 광고를 동기화할 때 Redis의 후보 목록과 JSON을 삭제했다. 이 변경이 로컬 캐시에 반영되는 흐름은 다음과 같다.
```te
광고 항목 비활성화
  → 동기화 과정에서 Redis 후보·JSON 삭제
  → API 프로세스의 로컬 캐시 만료·정리
  → 더 이상 사용하지 않는 JSON의 참조 해제
  → GC가 공간 회수
```

Redis에서 지웠다고 모든 API 프로세스의 로컬 캐시가 즉시 사라지진 않고, GC를 거치며 더 이상 조회되지 않는 데이터의 참조가 끊어진다.
물론 캐시가 여전히 참조하는 객체는 GC가 자주 돈다고 제거되지 않는다.

## 생존 heap이 줄면 GC까지의 여유도 줄어든다

이제 GC 빈도가 늘어난 이유를 살펴보자. Go는 `GOGC` 설정으로 생존 heap에 비례하는 추가 할당 여유를 정한다. 당시 `GOGC=100`이었고, Go 런타임의 메모리 제한 설정인 `GOMEMLIMIT`은 제한 없음으로 유지되고 있었다.

`GOGC=100`을 단순화하면 살아남은 양만큼 더 할당할 여유를 둔다는 뜻이다. 아래는 실제 관측값이 아닌 **설명용 예시**다. 두 경우 모두 할당률은 100 MiB/s로 같다고 가정한다.

| 항목 | 많이 보관할 때 | 적게 보관할 때 |
| --- | ---: | ---: |
| 생존 heap | 100 MiB | 50 MiB |
| 추가 할당 여유 | 약 100 MiB | 약 50 MiB |
| 다음 heap 목표 | 약 200 MiB | 약 100 MiB |
| GC 주기 근사치 | 약 1초 | 약 0.5초 |

**같은 속도로 할당해도, 할당할 여유가 작아지면 GC가 더 자주 실행될 수 있다.** 이번에 관측한 생존 heap 감소, 거의 같은 할당률, GC 빈도 증가는 이 원리와 일치한다.

예시는 생존 heap과 할당률이 일정하고 메모리 제한이 없다고 가정했으며, GC roots를 생략했다. GC roots는 스택이나 전역 변수처럼 GC가 참조를 따라가기 시작하는 출발점이다.

[Go 공식 GC 가이드](https://go.dev/doc/gc-guide#GOGC)의 목표식은 `생존 heap + (생존 heap + GC roots) × GOGC / 100`이다. 실제로는 목표에 맞춰 수집을 마치도록 GC를 미리 시작하므로, heap 목표를 정확한 GC 시작선으로 읽으면 안 된다. 표의 주기도 원리를 이해하기 위한 근사치다.

그렇다고 GC 횟수가 늘어난 비율만큼 CPU 비용도 늘었다고 계산할 수는 없다. 한 번의 GC에서 처리하는 양과 객체의 참조 구조에 따라 비용이 달라지기 때문이다.

![변화 전보다 GC 관련 CPU 비율이 높아진 Datadog 누적 영역 그래프](gc-cpu.png)

_GC 관련 CPU 비율도 높아졌다. 누적 영역의 전체 높이는 패널 구성요소의 합이며, GC 정지 시간을 나타내는 그래프는 아니다._

앞서 비교한 두 30분 구간에서 GC 관련 CPU 패널의 합은 6.87%에서 9.21%로 증가했다. 다만 여기에는 유휴 CPU를 사용하는 idle mark와 메모리를 운영체제에 돌려주는 scavenging도 포함된다. 전체를 요청 처리를 빼앗은 CPU나 프로그램이 멈춘 시간으로 해석하지 않았다.

## p95 응답시간도 줄었다

p95는 요청을 응답시간 순으로 세웠을 때 95% 지점의 값이다. 느린 쪽의 변화를 볼 수 있지만, 모든 요청의 속도를 대표하지는 않는다.

![연한 파란색 p95 응답시간이 낮아지는 흐름을 보여주는 Datadog latency 그래프](p95-latency.png)

_연한 파란색 선이 p95다. 앞쪽에서는 400~500ms 부근까지 반복해서 올라가다가, 뒤쪽에서는 300ms 안팎으로 낮아진다. 그림은 며칠간의 추이이며, 아래 표는 앞서 선택한 전후 30분 구간의 통계다._

같은 두 구간의 요청 통계를 비교하니 다음과 같았다.

| 지표 | 이전 | 이후 |
| --- | ---: | ---: |
| p95 응답시간 | 498ms | 354ms |
| 평균 응답시간 근사치 | 약 108ms | 약 108ms |
| 요청 수 | 1,670만 | 2,020만 |

평균은 화면에 반올림된 누적 처리시간을 요청 수로 나눈 근사치다. 평균은 거의 같고 p95가 줄었으므로, 모든 요청이 일률적으로 빨라졌다고 보기는 어렵다.

타기팅 조건을 검사하는 경로의 누적 CPU 표본 시간은 약 56% 줄었다. 객체를 많이 만들지 않는 문자열 비교도 있으므로, 검사 CPU가 줄면서 할당률은 유지될 수 있다. 다만 여러 인스턴스의 CPU 표본 감소를 개별 요청의 144ms 개선으로 환산할 수는 없다.

또한 [Go GC는 대부분 애플리케이션과 동시에 실행된다](https://go.dev/doc/gc-guide#Latency). 짧은 정지나 CPU 경쟁은 있지만, GC 빈도가 요청의 정지 시간과 일대일로 대응하지는 않는다. 다른 처리나 대기가 줄면 GC가 잦아져도 응답시간은 개선될 수 있다.

요청 수는 약 21% 늘었고 트래픽 구성도 통제하지 못했다. 느린 요청이 빨라졌을 수도, 빠른 요청의 비중이 늘었을 수도 있다. 광고 비활성화는 검사 비용 감소의 유력한 설명이지만, p95 개선에 얼마나 기여했는지는 미확정으로 남겼다.

## 다음에 같은 그래프를 만나면

이번 조사에서 구분하게 된 것은 초당 객체에 할당한 메모리, GC 후에도 사용 중인 메모리, GC 실행 빈도, 요청의 응답시간이다. 서로 영향을 주지만 같은 값은 아니었다.

다음에는 생존 heap과 할당률을 나눠 보고, 프로파일로 변화한 경로를 찾으려 한다. GC 빈도와 CPU 비용, 평균과 p95, 요청 구성도 함께 볼 것이다.

필요 없는 캐시를 유지하거나 GC 설정부터 바꿀 이유는 없다. 무엇이 줄고 무엇은 그대로인지 먼저 이해해야 한다. 이번에는 할당률이 거의 같았다는 사실이 GC 그래프를 읽는 단서였다.
