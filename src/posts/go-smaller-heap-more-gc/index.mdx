## 메모리는 줄었는데 GC 그래프는 올라갔다

운영 중인 Go 서버에서 메모리가 줄었는데 GC는 오히려 늘었다. 메모리를 덜 쓰면 GC도 할 일이 줄어들 것 같은데, 그래프는 반대로 움직였다.

변화 전후 각각 30분의 Datadog 지표를 비교했다. 서비스명은 생략했지만 수치는 당시 관측값이다. MiB는 메모리 크기 단위로, 1 MiB는 1,048,576바이트다.

| 지표 | 이전 | 이후 |
| --- | ---: | ---: |
| 생존 heap | 75.63 MiB | 48.89 MiB |
| 평균 heap 할당률 | 238.02 MiB/s | 239.87 MiB/s |
| 평균 GC 빈도 | 3.68회/초 | 6.01회/초 |

여러 인스턴스를 집계한 1분 지표값을 구간마다 평균 낸 결과다. 단일 서버를 계속 따라가며 측정한 값은 아니다. 특히 할당률과 GC 빈도는 누적 카운터를 집계해 계산하므로 인스턴스 교체의 영향도 받을 수 있다.

생존 heap은 약 35% 줄고 GC 빈도는 약 63% 늘었다. 그런데 새 메모리를 만드는 속도는 거의 같았다. 이를 이해하려면 메모리를 보는 기준부터 나눠야 했다.

## 먼저, 만드는 양과 남아 있는 양을 나눠 보자

heap은 프로그램에서 동적으로 할당한 객체를 두는 메모리 공간이다. 모든 Go 변수가 heap에 놓이지는 않지만, 여기서는 heap에 할당한 요청 데이터와 캐시에 집중하자.

참조는 프로그램이 객체를 계속 가리키는 연결이다. GC(Garbage Collector)는 이런 연결을 따라가며 도달할 수 있는 객체를 찾고, 더 이상 도달할 수 없는 객체의 공간을 회수한다. 프로그램이 계속 붙잡고 있는 객체를 임의로 버리지는 않는다.

메모리를 자료와 임시 메모를 올려놓는 작업대라고 생각해보자. 다음 요청에서도 쓰려고 캐시에 넣어 둔 광고 데이터는 보관하는 자료다. 요청마다 만들고 사용을 마치는 처리용 데이터는 임시 메모에 가깝다.

매초 임시 메모를 100장씩 만들어도 금방 사용을 마친다면 오래 남는 양은 적을 수 있다. 반대로 보관 자료는 새로 만들지 않아도 계속 자리를 차지한다. 보관 자료를 줄인다고 임시 메모를 만드는 속도까지 느려지는 것은 아니다.

**할당률은 초당 새로 할당하는 양이고, 생존 heap은 직전 GC에서 살아남은 양이다.** 하나는 만드는 속도이고 다른 하나는 남아 있는 양이다. 임시 메모도 GC 시점에 참조 중이라면 생존 heap에 포함될 수 있다.

사용이 끝나는 시점과 공간을 회수하는 시점도 다르다. 참조가 사라져도 GC가 회수하기 전에는 공간을 차지할 수 있고, 회수한 공간을 Go 런타임이 재사용하려고 보관할 수도 있다.

따라서 생존 heap을 프로세스의 전체 메모리로 읽으면 안 된다. 운영체제가 보는 물리 메모리 사용량인 RSS에는 스택 등 다른 영역도 들어간다. 이번에는 전체 Go 메모리 감소와 별개로, 생존 heap 자체가 줄어든 것을 확인했다.

## 줄어든 메모리는 캐시에 있었다

전후에 관측한 배포 버전과 GC 설정은 같았다. 무엇을 계속 보관하고 있는지 알아보기 위해 Pyroscope의 메모리 프로파일을 비교했다. 프로파일은 메모리를 할당한 코드 위치별로 사용량을 살펴볼 수 있는 자료다.

살아 있는 객체의 메모리를 보는 `inuse_space`에서 감소가 집중된 곳은 광고 JSON을 로컬 캐시에 넣는 지점이었다. 이곳의 표본 합은 약 72% 줄었고 나머지는 거의 같았다.

표본 합은 여러 인스턴스·시점의 프로파일을 더한 값으로, 동시에 점유한 메모리 총량이 아니다. 표본 수와 인스턴스 구성의 영향이 남으므로 감소 위치를 찾는 근거로 사용했다.

캐시는 Redis에서 읽어 압축을 푼 JSON을 보관했다. 유효 기간은 2분이고 만료 항목은 1분마다 정리했다. 따라서 코드가 같아도 조회하는 광고의 종류가 줄면 캐시에 남는 데이터는 달라질 수 있었다.

이후 같은 날 광고 항목 14만 건을 비활성화했다는 운영 정보를 전달받았다. 당시 코드에서는 비활성화된 항목을 동기화할 때 Redis의 후보 목록과 JSON을 삭제했다. 로컬 캐시까지 반영되는 흐름은 다음과 같다.

```text
광고 항목 비활성화
  → 동기화 과정에서 Redis 후보·JSON 삭제
  → API 프로세스의 로컬 캐시 만료·정리
  → 더 이상 사용하지 않는 JSON의 참조 해제
  → GC가 공간 회수
```

Redis에서 지웠다고 모든 API 프로세스의 로컬 캐시가 즉시 사라지는 것은 아니다. 만료와 정리를 거치며 더 이상 조회되지 않는 데이터의 참조가 끊어진다. 캐시가 여전히 참조하는 유효한 항목은 GC가 자주 돈다는 이유로 제거되지 않는다.

생존 heap 감소를 설명하는 유력한 경로다. 다만 실행·동기화 시각과 지표 급락 구간을 대조하지 못했고, 캐시 항목 수의 실제 감소량도 확보하지 못했다. 원인을 완전히 입증한 것은 아니다.

### 14만 건을 줄였는데 할당률은 왜 비슷했을까?

전체 보관 대상 수와 한 요청에서 처리하는 수가 달랐기 때문이다. 당시 조회 코드는 후보가 200개를 넘으면 무작위로 200개를 골라 JSON을 읽고 해석했다.

예를 들어 한 요청의 후보가 1,000개에서 300개로 줄어도, 선택하는 수는 둘 다 200개다. 이 숫자는 구조를 설명하기 위한 예시다. 여러 요청에 걸쳐 캐시에 보관하는 광고의 종류는 줄면서, 요청마다 JSON을 처리하며 만드는 객체의 양은 비슷할 수 있다.

실제 상한 도달 비율은 측정하지 않았다. 후보 목록 복사와 섞기는 상한 적용 전이므로 모든 비용이 같다는 뜻도 아니다. 다만 **상주 메모리 감소와 할당률 유지가 양립할 수 있는 코드 경로**는 확인했다.

## 생존 heap이 줄면 GC까지의 여유도 줄어든다

이제 GC 빈도가 늘어난 이유를 살펴보자. Go는 `GOGC` 설정으로 생존 heap에 비례하는 추가 할당 여유를 정한다. 당시 `GOGC=100`이었고, Go 런타임의 메모리 제한 설정인 `GOMEMLIMIT`은 제한 없음으로 유지되고 있었다.

`GOGC=100`을 단순화하면 살아남은 양만큼 더 할당할 여유를 둔다는 뜻이다. 아래는 실제 관측값이 아닌 **설명용 예시**다. 두 경우 모두 할당률은 100 MiB/s로 같다고 가정한다.

| 항목 | 많이 보관할 때 | 적게 보관할 때 |
| --- | ---: | ---: |
| 생존 heap | 100 MiB | 50 MiB |
| 추가 할당 여유 | 약 100 MiB | 약 50 MiB |
| 다음 heap 목표 | 약 200 MiB | 약 100 MiB |
| GC 주기 근사치 | 약 1초 | 약 0.5초 |

**같은 속도로 할당해도, 할당할 여유가 작아지면 GC가 더 자주 실행될 수 있다.** 이번에 관측한 생존 heap 감소, 거의 같은 할당률, GC 빈도 증가는 이 원리와 일치한다.

예시는 생존 heap과 할당률이 일정하고 메모리 제한이 없다고 가정했으며, GC roots를 생략했다. GC roots는 스택이나 전역 변수처럼 GC가 참조를 따라가기 시작하는 출발점이다.

[Go 공식 GC 가이드](https://go.dev/doc/gc-guide#GOGC)의 목표식은 `생존 heap + (생존 heap + GC roots) × GOGC / 100`이다. 실제로는 목표에 맞춰 수집을 마치도록 GC를 미리 시작하므로, heap 목표를 정확한 GC 시작선으로 읽으면 안 된다. 표의 주기도 원리를 이해하기 위한 근사치다.

그렇다고 GC 횟수가 늘어난 비율만큼 CPU 비용도 늘었다고 계산할 수는 없다. 한 번의 GC에서 처리하는 양과 객체의 참조 구조에 따라 비용이 달라지기 때문이다.

이번에는 GC 관련 CPU 패널의 합도 6.87%에서 9.21%로 증가했다. 다만 여기에는 유휴 CPU를 사용하는 idle mark와 메모리를 운영체제에 돌려주는 scavenging도 포함된다. 전체를 요청 처리를 빼앗은 CPU나 프로그램이 멈춘 시간으로 해석하지 않았다.

## 그런데 p95 응답시간도 줄었다

p95는 요청을 응답시간 순으로 세웠을 때 95% 지점의 값이다. 느린 쪽의 변화를 볼 수 있지만, 모든 요청의 속도를 대표하지는 않는다. 같은 두 구간의 요청 통계를 비교하니 다음과 같았다.

| 지표 | 이전 | 이후 |
| --- | ---: | ---: |
| p95 응답시간 | 498ms | 354ms |
| 평균 응답시간 근사치 | 약 108ms | 약 108ms |
| 요청 수 | 1,670만 | 2,020만 |

평균은 화면에 반올림된 누적 처리시간을 요청 수로 나눈 근사치다. 평균은 거의 같고 p95가 줄었으므로, 모든 요청이 일률적으로 빨라졌다고 보기는 어렵다.

타기팅 조건을 검사하는 경로의 누적 CPU 표본 시간은 약 56% 줄었다. 객체를 많이 만들지 않는 문자열 비교도 있으므로, 검사 CPU가 줄면서 할당률은 유지될 수 있다. 다만 여러 인스턴스의 CPU 표본 감소를 개별 요청의 144ms 개선으로 환산할 수는 없다.

또한 [Go GC는 대부분 애플리케이션과 동시에 실행된다](https://go.dev/doc/gc-guide#Latency). 짧은 정지나 CPU 경쟁은 있지만, GC 빈도가 요청의 정지 시간과 일대일로 대응하지는 않는다. 다른 처리나 대기가 줄면 GC가 잦아져도 응답시간은 개선될 수 있다.

요청 수는 약 21% 늘었고 트래픽 구성도 통제하지 못했다. 느린 요청이 빨라졌을 수도, 빠른 요청의 비중이 늘었을 수도 있다. 광고 비활성화는 검사 비용 감소의 유력한 설명이지만, p95 개선에 얼마나 기여했는지는 미확정으로 남겼다.

## 다음에 같은 그래프를 만나면

이번 조사에서 구분하게 된 것은 만드는 속도, 남아 있는 양, GC가 실행되는 빈도, 요청이 끝나는 시간이다. 서로 영향을 주지만 같은 값은 아니었다.

다음에는 생존 heap과 할당률을 나눠 보고, 프로파일로 변화한 경로를 찾으려 한다. GC 빈도와 CPU 비용, 평균과 p95, 요청 구성도 함께 볼 것이다.

필요 없는 캐시를 유지하거나 GC 설정부터 바꿀 이유는 없다. 무엇이 줄고 무엇은 그대로인지 먼저 이해해야 한다. 이번에는 할당률이 거의 같았다는 사실이 GC 그래프를 읽는 단서였다.
