- 🔗 https://github.com/grpc/grpc-go/pull/9252

grpc-go testing 부분에 새롭게 기여한 내용을 기록.
내부 구현에 결합된 테스트를 실제 gRPC 호출을 사용하는 E2E 테스트로 수정했다. 수정했던 issue는 여전히 open 상태인데 해당 패키지(outlierdetection)가 내부 구현에 의존하는 테스트가 주로 작성된 걸로 보인다. 

처음에는 단순히 테스트 파일을 옮기는 작업으로 생각했지만, outlierdetection의 **internal timer와 concrete balancer**를 직접 조작하던 방식도 함께 걷어냈다. 테스트 관찰 지점을 내부 구현에서 사용자가 경험하는 동작으로 옮기는 작업이었다.

## 검증하려던 동작

기존 테스트(`TestPickFirstHealthListenerDisabled`) 동작을 이해하려면 gRPC client가 요청을 보내는 경로부터 봐야한다.

애플리케이션은 `ClientConn`이라는 channel을 만든다. resolver가 찾은 backend 주소 중 하나를 load-balancing policy가 고르고, 선택된 주소와의 실제 연결은 `SubConn`이 관리한다.

```bash
애플리케이션
  ↓ RPC 호출
ClientConn (channel)
  ↓ resolver가 backend 주소 제공
load-balancing policy
  ↓ 하나의 주소 선택
SubConn
  ↓ transport 연결
backend
```

`pick_first`가 health listener를 사용하지 않는 구성이다.

오류를 반환하는 RPC가 반복되어도 outlier detection의 ejection 처리 때문에 channel connectivity가 `TRANSIENT_FAILURE`(일시 실패)로 바뀌면 안 된다는 것을 확인한다.

여기서 먼저 구분할 것이 있다. channel이 `READY`라는 사실과 RPC가 성공했다는 사실은 다르다.

- `READY`: RPC를 보낼 transport 연결이 준비된 상태
- RPC 성공: 서버 메서드가 오류 없이 끝난 상태

테스트 backend는 연결 자체는 받아들이지만 모든 RPC에 오류를 반환한다. 그래서 RPC 호출은 실패해도 transport가 살아 있으면 channel은 `READY`일 수 있다.

이 상태에서 outlier detection이 endpoint를 ejection하더라도, health listener가 비활성화된 `pick_first`의 connectivity 상태까지 오염시키지 않는지가 검증 대상이다.

## outlier detection과 pick_first의 역할

grpc-go의 outlier detection은 별도 health-check RPC를 보내는 대신 실제 RPC 결과를 endpoint별로 모은다.

일정한 `interval`마다 성공률과 실패율을 계산하고, 비정상으로 판단한 endpoint를 일정 시간 ejection한다.

```bash
RPC 완료
  ↓
endpoint별 성공/실패 기록
  ↓ interval마다 통계 평가
비정상 endpoint ejection
```

outlier detection이 직접 SubConn을 고르지는 않는다. child policy의 picker를 감싸서 RPC 결과를 관찰할 뿐이다.

실제 address와 SubConn 선택은 child policy가 맡는다. 이 테스트의 policy 관계는 아래와 같다.

```bash
outlier_detection_experimental
  └── childPolicy: pick_first
```

`outlier_detection_experimental`은 어느 endpoint가 비정상인지 판단하고, `pick_first`는 연결 가능한 첫 address를 선택한다.

예를 들어 resolver가 `A`, `B`, `C` 세 backend 주소를 전달했다고 하자. `pick_first`는 먼저 A와 연결을 시도한다.

A의 transport가 `READY`가 되면 이후 RPC는 모두 A로 보낸다. A의 연결이 끊기거나 실패해야 그다음 주소 B에 연결을 시도한다.

`round_robin`처럼 RPC마다 A, B, C를 번갈아 고르지는 않는다.

```bash
resolver: [A, B, C]
             ↓
pick_first: A 연결 시도
             ↓
A가 READY: 이후 RPC는 A로 전송
A 연결 실패: B 연결 시도
```

서버 메서드가 반환한 RPC 오류와 A의 transport 연결 실패는 다르다.

이 테스트처럼 연결은 살아 있지만 RPC만 실패하는 경우, `pick_first`가 곧바로 B로 넘어가거나 channel을 `TRANSIENT_FAILURE`로 만들면 안 된다.

`pick_first`는 resolver state에 health listener 활성화 attribute가 있을 때만 health listener를 등록한다. 이 테스트에서는 그 attribute를 전달하지 않는다.

## 기존 테스트가 내부 구현을 알아야 했던 이유

기존 테스트는 실제 backend를 띄우고 실패 RPC를 발생시켰다. 문제는 ejection을 실행하는 방식이다.

자동 timer가 실행되지 않도록 interval을 `300s`로 두고, 실패 RPC를 만든 뒤 private 메서드 `intervalTimerAlgorithm()`을 직접 호출했다.

```go
od.intervalTimerAlgorithm()
```

이 메서드를 호출하려면 테스트가 `*outlierDetectionBalancer` pointer를 얻어야 한다.

`grpc.NewClient()`가 service config를 해석해 만든 balancer는 외부에 노출되지 않는다. 기존 테스트는 stub balancer를 policy로 등록해 실제 balancer 생성을 가로챘다.

```bash
ClientConn
  ↓ service config가 테스트용 stub 선택
stub balancer
  ↓ 실제 outlierDetectionBalancer 생성
outlierDetectionBalancer
  ↓ pointer를 테스트에 전달
pick_first
```

stub balancer가 알고리즘을 대체한 것은 아니다. 실제 balancer를 감싸서 concrete pointer와 테스트용 `LBConfig`을 넘기는 hook 역할을 했다.

하지만 이 구조에서는 timer callback 이름이나 balancer 생성 경로가 바뀌기만 해도, production 동작이 그대로여도 테스트를 함께 고쳐야 한다.

## 실제 gRPC 경로로 바꾸기

업데이트된 테스트는 balancer instance를 꺼내지 않는다.

JSON service config에 `outlier_detection_experimental`과 `pick_first`를 직접 설정하고, `grpc.NewClient()`로 `ClientConn`을 만든다. 그리고 생성된 client가 해당 channel을 통해 실제 RPC를 호출하게 한다.

```go
cc, err := grpc.NewClient(target, opts...)
if err != nil {
    t.Fatal(err)
}
defer cc.Close()

client := testgrpc.NewTestServiceClient(cc)
for range 10 {
    _, _ = client.EmptyCall(ctx, &testpb.Empty{})
}
```

`grpc.NewClient()`의 결과인 `ClientConn`은 resolver, service config, balancer, SubConn과 connectivity를 관리하는 gRPC channel이다.

반면 `testgrpc.NewTestServiceClient(cc)`는 새 연결을 만들지 않는 typed client stub이다. `EmptyCall()`은 결국 같은 `ClientConn`의 RPC 경로로 들어간다.

새 테스트는 interval을 `50ms`로 설정한다. 실패 RPC를 10번 호출한 뒤, 약 세 interval인 `150ms` 동안 channel이 계속 `READY`인지 확인한다.

실제 timer와 실제 picker가 모두 동작하므로 `intervalTimerAlgorithm()`의 존재나 호출 방법을 테스트가 알 필요가 없다.

## 이 PR이 바꾸지 않은 것

이번 PR은 outlier detection 알고리즘이나 `pick_first`의 health listener 동작을 수정하지 않았다. 새 API도 없고 production 코드 변경도 없다.

[issue #8658](https://github.com/grpc/grpc-go/issues/8658)에서 말한, 내부 구현에 강하게 결합된 테스트를 가능한 범위에서 E2E 스타일로 옮기는 작업의 한 단계다.

모든 테스트를 E2E로 바꿔야 한다는 뜻은 아니다.

이 경우 기존 테스트가 확인하려던 결과가 private method 호출 자체가 아니라 channel connectivity의 경계였다. 실제 client가 보는 경로가 더 적절한 관찰 지점이었다.

테스트가 내부 상태를 정밀하게 검사할수록 구현 변경에는 민감해진다.

반대로 사용자가 실제로 겪는 동작을 검증하면 내부 구조는 바꿀 여지를 남길 수 있다. 이번 PR은 timer를 직접 호출하지 않는 작은 변경으로 그 차이를 잘 보여준다.
