- 🔗 https://github.com/grpc/grpc-go/pull/9252

grpc-go testing 부분에 새롭게 기여한 내용을 기록. <br/>
내부 구현에 결합된 테스트를 실제 gRPC 호출을 사용하는 E2E 테스트로 수정했다. 수정했던 issue는 여전히 open 상태인데 해당 패키지(outlierdetection)가 내부 구현에 의존하는 테스트가 주로 작성된 걸로 보인다.

처음에는 단순히 테스트 파일을 옮기는 작업으로 생각했고 큰 그림에서는 맞는 방향이었지만, outlierdetection의 **internal timer와 concrete balancer**를 직접 조작하던 방식도 함께 걷어냈다. 테스트 관찰 지점을 내부 구현에서 사용자가 경험하는 동작으로 옮기는 작업이었다.

## 검증하려던 동작

기존 테스트(`TestPickFirstHealthListenerDisabled`) 동작을 이해하려면 gRPC client가 요청을 보내는 경로부터 봐야한다.

클라이언트는 `ClientConn`이라는 channel을 만들고 resolver가 찾은 backend 주소 중 하나를 load-balancing policy가 고른다. 선택된 주소의 실제 연결은 `SubConn`이 관리한다.

```bash
애플리케이션
  ↓ RPC 호출
ClientConn (channel)
  ↓ resolver가 backend 주소 제공
load-balancing policy
  ↓ 하나의 주소 선택
SubConn
  ↓ transport 연결
backend
```

여기서 먼저 구분할 것이 있다. channel이 `READY`라는 사실과 RPC가 성공했다는 사실은 다르다.

- `READY`: RPC를 보낼 transport 연결이 준비된 상태
- RPC 성공: 서버 메서드가 오류 없이 끝난 상태

remote server 프로세스와 TCP/HTTP2 transport 연결은 살아 있어도, 서버의 RPC handler가 계속 오류를 반환할 수 있다.

이 경우 connection 관점에서는 `READY`지만, 애플리케이션 관점에서는 해당 endpoint가 요청을 정상 처리하지 못하는 상태다.

outlier detection은 transport 연결 단절만 감지하는 기능이 아니다.

별도 ping이나 임의의 health-check RPC를 보내지 않고, 애플리케이션이 실제로 호출한 RPC 결과를 endpoint별로 관찰해 비정상 endpoint를 찾는다.

그래서 RPC 실패율이 높으면 해당 endpoint를 일정 시간 논리적으로 ejection할 수 있다.

ejection은 connection을 끊는 일이 아니라, load balancer가 해당 endpoint를 당분간 선택하지 않도록 하는 조치다.

정상 endpoint가 여러 개라면 load balancer는 실패하는 endpoint를 제외하고 다른 endpoint로 트래픽을 보낼 수 있다.

실제 connection 상태와 애플리케이션 수준의 endpoint 평가는 이처럼 서로 다른 층위의 정보다.

이 테스트의 service config는 `outlier_detection_experimental` 아래에 `pick_first`를 child policy로 둔다.

이 구성에서는 resolver가 `pick_first`에 health listener 사용을 요청하는 attribute를 전달하지 않는다.

health listener는 outlier detection이 endpoint를 ejection했을 때, 그 endpoint를 일시적으로 제외하라는 health 신호를 child policy에 전달하는 통로다.

listener를 등록한 `pick_first`는 이 신호를 받아 transport가 살아 있어도 해당 SubConn을 사용 대상에서 제외할 수 있다.

하지만 이 테스트처럼 listener가 없는 구성에서는 ejection 판단이 raw transport connectivity를 바꾸면 안 된다.

따라서 오류 RPC가 반복되어도, 실제 transport 실패가 아닌 이유로 channel connectivity가 `TRANSIENT_FAILURE`(일시 실패)로 바뀌지 않는지 확인한다.

테스트 코드에서 test server는 연결 자체를 받아들이지만 모든 RPC에 오류를 반환한다.
그래서 RPC 호출은 실패해도 transport가 살아 있으면 channel은 `READY`일 수 있다.

즉, 이 테스트는 outlier detection이 RPC 실패를 endpoint 평가에 사용하는 것과 그 결과를 transport connection 실패로 오인하는 것을 구분해 검증한다.

## outlier detection과 pick_first의 역할

grpc-go의 outlier detection은 별도 health-check RPC나 ping을 보내지 않는다. 애플리케이션이 원래 호출한 RPC의 완료 결과를 endpoint별로 모으는 passive health checking 방식이다.

RPC가 끝나면 outlier detection은 해당 RPC가 처리한 SubConn과 `DoneInfo.Err`를 확인한다.

오류가 없으면 성공, 오류가 있으면 실패로 기록하고 설정한 `interval`마다 stats를 평가한다.

테스트의 `TestService/EmptyCall`은 실패 표본을 만들기 위한 fixture다.

운영 환경에서는 outlier detection이 새 요청을 만들지 않으며, 서비스가 보내는 실제 메서드와 request payload를 그대로 관찰한다.

일정한 `interval`마다 성공률과 실패율을 계산하고, 비정상으로 판단한 endpoint를 일정 시간 ejection한다.

```bash
RPC 완료
  ↓
endpoint별 성공/실패 기록
  ↓ interval마다 통계 평가
비정상 endpoint ejection
```

outlier detection이 직접 SubConn을 고르지는 않는다. child policy의 picker를 감싸서 RPC 결과를 관찰할 뿐이다.

실제 address와 SubConn 선택은 child policy가 맡는다. 이 테스트의 policy 관계는 아래와 같다.

```bash
outlier_detection_experimental
  └── childPolicy: pick_first
```

`outlier_detection_experimental`은 어느 endpoint가 비정상인지 판단하고, `pick_first`는 연결 가능한 첫 address를 선택한다.

예를 들어 resolver가 `A`, `B`, `C` 세 backend 주소를 전달했다고 하자. `pick_first`는 먼저 A와 연결을 시도한다.

A의 transport가 `READY`가 되면 이후 RPC는 모두 A로 보낸다. A의 연결이 끊기거나 실패해야 그다음 주소 B에 연결을 시도한다.

`round_robin`처럼 RPC마다 A, B, C를 번갈아 고르지는 않는다.

```bash
resolver: [A, B, C]
             ↓
pick_first: A 연결 시도
             ↓
A가 READY: 이후 RPC는 A로 전송
A 연결 실패: B 연결 시도
```

서버 메서드가 반환한 RPC 오류와 A의 transport 연결 실패는 다르다.

이 테스트처럼 연결은 살아 있지만 RPC만 실패하는 경우, `pick_first`가 곧바로 B로 넘어가거나 raw channel connectivity를 `TRANSIENT_FAILURE`로 만들면 안 된다.

health listener를 등록한 구성이라면 outlier detection의 ejection 신호를 child policy가 받아 endpoint를 제외할 수 있다.

이번 테스트는 그 listener가 없는 경우에도 transport 연결 상태가 정확히 보존되는지를 확인한다.

## 기존 테스트가 내부 구현을 알아야 했던 이유

기존 테스트도 실제 backend에 실패 RPC를 보냈다. 확인하려던 결과 역시 “outlier detection이 동작한 뒤에도 channel이 `READY`인가”였다.

다만 outlier detection은 RPC가 끝나는 즉시 ejection을 계산하지 않는다. RPC 결과를 endpoint별 counter에 쌓아 두고, `interval`이 지났을 때 timer가 counter를 교체한 뒤 ejection 알고리즘을 실행한다.

테스트에서 실제 `300s`를 기다릴 수는 없다. 반대로 interval을 너무 짧게 두면 필요한 실패 counter가 쌓이기 전에 timer가 실행돼 테스트가 비결정적이 된다.

기존 테스트는 다음 순서로 이 문제를 피했다.

1. interval을 `300s`로 설정해 timer가 테스트 중 자동 실행되지 않게 한다.
2. 실패 RPC를 필요한 만큼 호출해 counter를 채운다.
3. timer를 기다리는 대신 private 메서드 `intervalTimerAlgorithm()`을 직접 호출한다.
4. ejection 알고리즘이 끝난 뒤 channel 상태를 확인한다.

```go
od.intervalTimerAlgorithm()
```

private 메서드를 호출하려면 테스트가 `*outlierDetectionBalancer` pointer를 얻어야 한다. `grpc.NewClient()`가 service config를 처리하면서 만든 balancer는 외부 API로 노출되지 않는다.

그래서 기존 테스트는 `bf`라는 `stub.BalancerFuncs` 값을 실제 balancer가 아니라 테스트용 builder/factory로 사용했다.

`bf`를 테스트 전용 policy 이름으로 registry에 등록하고, service config가 그 policy를 선택하도록 만들었다.

```bash
bf: 테스트용 builder/factory
  ↓ stub.Register(t.Name(), bf)
service config: t.Name() policy 선택
  ↓ ClientConn이 stub의 Init 호출
stub Init
  ↓ 실제 outlierDetectionBalancer 생성
테스트가 pointer를 전달받아 intervalTimerAlgorithm() 호출
```

stub은 outlier detection 알고리즘을 대체하지 않았다. `Init`에서 실제 `outlierDetectionBalancer`를 만들고, concrete pointer와 테스트용 `LBConfig`을 넘기는 test hook 역할만 했다.

이 방식은 테스트를 빠르고 결정적으로 만들었다. 대신 timer callback 이름이나 balancer 생성 경로가 바뀌기만 해도, production 동작이 그대로여도 테스트를 함께 고쳐야 했다.

## 실제 gRPC 경로로 바꾸기

이번 PR에서 바꾼 테스트는 balancer instance를 꺼내지 않는다.

JSON service config에 `outlier_detection_experimental`과 `pick_first`를 직접 설정하고, `grpc.NewClient()`로 `ClientConn`을 만든다. 그리고 생성된 client가 해당 channel을 통해 실제 RPC를 호출하게 한다.

```go
cc, err := grpc.NewClient(target, opts...)
if err != nil {
    t.Fatal(err)
}
defer cc.Close()

client := testgrpc.NewTestServiceClient(cc)
for range 10 {
    _, _ = client.EmptyCall(ctx, &testpb.Empty{})
}
```

`grpc.NewClient()`의 결과인 `ClientConn`은 resolver, service config, balancer, SubConn과 connectivity를 관리하는 gRPC channel이다.

반면 `testgrpc.NewTestServiceClient(cc)`는 새 연결이나 balancer를 만들지 않는 typed client stub이다. `EmptyCall()`은 결국 같은 `ClientConn`의 RPC 경로로 들어간다.

새 테스트는 interval을 `50ms`로 설정한다. 실패 RPC를 10번 호출한 뒤, 약 세 interval인 `150ms` 동안 channel이 계속 `READY`인지 확인한다.

실제 timer와 실제 picker가 모두 동작하므로 `intervalTimerAlgorithm()`의 존재나 호출 방법을 테스트가 알 필요가 없다.

## PR이 변경하지 않은 것

이번 PR은 outlier detection 알고리즘이나 `pick_first`의 health listener 동작을 수정하지 않았다. <br/>
[issue #8658](https://github.com/grpc/grpc-go/issues/8658)에서 언급한대로 내부 구현에 강하게 결합된 테스트를 가능한 범위에서 E2E 스타일로 옮기는 작업 중 하나로, 새로운 API 추가나 production 코드 변경도 없었다.

모든 종류의 테스트를 E2E로 바꿔야 하는 것은 아니다. 이번 경우 기존 테스트가 검증하려던 결과는 private method 호출 자체가 아니라 channel connectivity의 경계였기 때문에, 실제 client가 보는 동작이 더 적절한 관찰 지점이었다.

테스트가 내부 상태를 디테일하게 검증할수록 구현 변경은 어려워진다. 반대로 사용자가 실제로 보는 동작을 테스트하면 내부 구조는 변경할 여지를 남길 수 있다. 이번 PR은 timer를 직접 호출하지 않는 작은 변경으로 그 차이를 잘 보여준다.
