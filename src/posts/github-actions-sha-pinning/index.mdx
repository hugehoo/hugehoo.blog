## CI 실패 원인 파악

사내 레포지토리에서 빌드와 배포가 비슷한 시점에 실패해서 확인해보니 GitHub Actions의 `Set up job` 단계에서 멈춰 있었다.
실패 로그에서 외부 액션의 소스 압축파일을 다운받는 요청이 404를 반환하고 있었다.

문제가 된 액션(`hashicorp/vault-action`)은 HashiCorp가 관리하는 GitHub 액션으로, 사내에선 해당 액션의 특정 커밋 SHA를 고정해서 사용하는데, 해당 SHA 버전을 찾을 수 없어 문제가 발생한 셈이었다. 

데브옵스 지식이 얕은 입장에서, 왜 외부 액션을 특정 커밋에 고정해서 사용하는 것인지, 단순히 최신 버전을 사용하면 이런 문제를 피할 수 있는 것 아닌가 의문이 들었다. 

이번 글은 내가 직접 이슈 대응한 내용은 아니고, 데브옵스 개발자분과 보안 담당자 분의 액션을 토대로 해당 이슈의 원인과 대응 방법을 기록했다.

## Vault 액션은 누가 관리하는 코드일까

위에서 언급했듯 [Vault Action](https://github.com/hashicorp/vault-action)은 HashiCorp가 관리하는 GitHub 액션으로 워크플로에서 Vault에 인증하고 필요한 비밀정보를 가져오는 등의 작업을 수행한다. 우리(회사)가 직접 작성한 코드가 아닌 외부 저장소(hashicorp)에서 가져와 실행하는 코드다.

사내에서는 여러 빌드·배포 워크플로는 공용 액션을 통해 이 액션을 사용 중이었고, 공용 액션 안에서 Vault 액션을 특정 커밋 SHA로 지정했다. (SHA: Secure Hash Algorithm, Git에서 커밋을 식별하는 해시값이다.)

```yaml
uses: hashicorp/vault-action@4c06c5ccf5c0761b6029f56cfb1dcf5565918a3b
```

위 라인은 “실행할 때마다 최신 코드를 가져와라”가 아니라 “이 커밋의 코드를 가져와라”라는 뜻으로 당시 이 SHA는 v3.4.0에 해당했다.

따라서 우리 저장소에 변경이 없더라도 CI runner가 hashicorp의 코드를 다운받지 못하면 작업을 시작할 수 없다. 일종의 의존성 문제로도 볼 수 있겠다. 실제 실패 지점도 Vault에 인증을 요청하는 단계에 도달하기 전이었다.

```text
빌드·배포 작업 시작
  → 사용할 액션 준비
  → 공용 액션이 참조하는 Vault 액션 다운로드
  → GitHub codeload에서 404 반환
  → Set up job 실패
```

## 404지만 커밋이 사라진 것은 아니었다
특정 SHA에서 404 가 뜨길래 커밋이 사라졌나 싶었지만 hashicorp 쯤 되는 회사에서 이미 릴리즈된 커밋을 날려먹기도 쉽지 않을거라 생각했다.
커밋이 실제로 삭제된 것은 아닌 이유는 해당 SHA를 지정한 `git fetch`가 성공했기 때문이고, 같은 버전인 `v3.4.0`도 태그를 지정한 다운로드 경로에서도 정상적으로 내려받을 수 있었다.

당시 확인된 결과를 정리하면 다음과 같다.

| 접근 방법                                | 관측 결과 |
| ---------------------------------------- | --------- |
| `v3.4.0` SHA의 압축파일 다운로드 | 404       |
| 해당 SHA를 지정한 `git fetch`            | 성공      |
| `v3.4.0` 태그를 지정한 압축파일 다운로드 | 성공      |
| `v4.0.0` SHA의 압축파일 다운로드           | 성공      |

GitHub의 codeload는 저장소 내용을 압축파일로 내려주는 서비스인데 커밋을 Git으로 가져오는 것과 해당 커밋의 압축파일을 HTTP로 내려받는 것은 접근 경로가 다르다.

이때는 특정 SHA의 압축파일을 제공하는 경로에 문제가 있다고 추정했다. 다만 **GitHub 내부에서 왜 404가 발생했는지까지 확인한 것은 아니다.** 모든 SHA 다운로드가 실패한 것도 아니어서, GitHub 전체 장애라고 일반화할 근거도 없었다.

또 러너에 필요한 액션의 캐시가 없을 때 실패한다는 보고가 있었다. 이미 코드를 가지고 있는 실행과 새로 다운로드해야 하는 실행은 결과가 다를 수 있다는 점도 함께 봐야 했다.

### 동일한 버전(v3.4.0)에서 SHA vs 태그 다운로드의 차이
같은 커밋을 가리킨다면 받는 소스 코드는 당연히 동일하고 차이점은 코드를 지정하는 방식에서 갈린다.

``` text
- SHA: 고유 번호 4c06c5…인 저장본을 주세요.
- Tag: v3.4.0이라는 이름표가 붙은 저장본을 주세요.
```

당시에는 다음 관계였습니다.
v3.4.0 태그가 동일한 `4c06c5…` 커밋을 가리킨다면 어느 쪽으로 요청하든 동일한 소스 코드가 나와야 한다.
결정적으로 차이는 직접 다운로드할 때 사용하는 URL이 달랐다.
``` text
SHA로 요청
…/tar.gz/4c06c5ccf5c0761b6029f56cfb1dcf5565918a3b

태그로 요청
…/tar.gz/refs/tags/v3.4.0
```
같은 소스를 요청해도 GitHub가 이 두 요청을 처리하는 과정에서 경로가 달라지니 한쪽만 실패할 수 있다. 이번 이슈가 이런 케이스였던 걸로 유추한다. (GitHub에서는 압축파일을 요청에 따라 생성하고 일정 기간 캐시한다고 설명하는데, 이번 장애가 구체적으로 캐시 문제였는지는 확인할 수 없었다.)
SHA는 특정 저장본을 직접 지정하지만 태그는 관리자가 다른 커밋으로 옮길 수 있는 이름표일 뿐이다. 그래서 **실행할 코드를 정확히 고정하기 위해 SHA를 사용한다.**

## SHA pinning은 유지, 버전을 업데이트

같은 버전의 태그 다운로드는 정상 동작했기 때문에 SHA pinning(고정)을 잠시 풀고 `v3.4.0` 태그를 사용하는 방안이 논의됐지만
실제로 반영된 수정은 조금 달랐다. 시큐 매니저분이 정상 다운로드되는 **v4.0.0의 SHA로 교체하는 PR**을 생성했고 이를 반영한 뒤 실패했던 작업을 재실행했다.

```diff
# SHA pinning 정책은 유지

- uses: hashicorp/vault-action@4c06c5ccf5c0761b6029f56cfb1dcf5565918a3b # v3.4.0
+ uses: hashicorp/vault-action@892a26828f195e65540a40b4768ae4571f51ebfc # v4.0.0
```

`v4.0.0`은 **vault-action의 lastest version**으로, 위 대응 방식을 보고 왜 굳이 SHA를 pinning하는지 그저 latest 태그를 사용하면 되는게 아닌가 의문이 들었다.

## 그런데 왜 SHA를 고정할까

태그를 쓰면 읽기도 편한데 굳이 긴 해시값을 쓰는 이유는 무엇일까.
액션 버전을 지정하는 방법을 비교해 보자.

| 참조 방식   | 실행할 코드가 정해지는 기준              |
| ----------- | ---------------------------------------- |
| `@main`     | 실행 시점에 main 브랜치가 가리키는 커밋  |
| `@v4`       | 실행 시점에 v4 태그가 가리키는 커밋      |
| `@v4.0.0`   | 실행 시점에 v4.0.0 태그가 가리키는 커밋  |
| `@892a268…` | 지정한 커밋. 실제 설정에는 전체 SHA 사용 |

첫번째 방식을 택하면 메인 브랜치가 갱신될 때 `@main`으로 실행하는 코드도 당연히 바뀐다. latest 태그를 사용하는 방식으로 볼 수 있다.
`@v4`처럼 메이저 버전 태그를 최신 v4 릴리스로 옮겨 주는 방식도 있다. 이 경우 워크플로 파일을 수정하지 않아도 다음 실행에서는 다른 코드가 동작할 수 있다.

`@v4.0.0`처럼 버전 전체를 적은 태그는 특정 릴리스를 가리키려는 의도가 더 분명하다. 다만 일반적인 Git 태그 자체는 mutable하기 때문에 GitHub의 immutable release로 보호되는 태그와도 구분해야 한다.

SHA로 고정하면 적어도 액션의 소스가 나도 모르게 다른 커밋으로 변경되는 것을 방지할 수 있다.
어제 성공한 배포와 오늘 실패한 배포가 같은 액션 코드를 사용했는지 확인하기도 쉬워진다.

보안 측면에서도 의미가 있다. 액션은 워크플로에 부여된 권한과 전달된 비밀정보를 사용할 수 있다. 특히 인증을 담당하는 액션이라면, 외부 저장소의 변경이 검토 없이 실행되는 상황을 줄일 필요가 있다.
[GitHub의 외부 액션 보안 가이드](https://docs.github.com/en/actions/reference/security/secure-use#using-third-party-actions)도 전체 커밋 SHA로 참조를 고정해 외부 코드 변조 위험을 줄이는 방법을 설명한다.
SHA가 코드의 안전성을 검증해 주는 것은 아니지만 **어떤 버전을 실행할지 고정하는 것과, 해당 코드의 안전성을 검토하는 것은 별개의 일**이다.

## 매번 최신 버전을 사용하면 안 될까

자동으로 최신 버전을 따라가면 업데이트를 직접 챙기는 부담을 줄일 수 있고, 버그 수정이나 보안 패치를 빠르게 받을 수도 있다. 대신 변경이 적용되는 시점도 외부 저장소의 업데이트에 따라 결정된다. 즉 우리 runner가 실행하는 코드가 어제 다르고 오늘 다를 수 있다. **좋고 나쁘고의 문제라기 보다 트래킹 자체가 어려워진다.**

이번에는 버전 업데이트로 대응했지만 항상 최신 버전을 사용하는 것이 더 안정적이라 말하기도 어렵다. 최신 버전에도 얼마든지 버그가 있을 수 있고 **다운로드 서비스 장애는 참조 방식과 관계없이 발생할 수 있다.**(이번 케이스)

내가 이해한 현실적인 운영 방식은 **검증한 버전의 SHA를 고정하고, 새 버전은 PR을 통해 명시적으로 업데이트 하는 것**이다.
pinning을 하되 필요시 마다 명시적으로 업데이트하여 트래킹 하는 것으로 이해했다.

## 마무리
vault-action의 404를 계기로 커밋 SHA 고정과 최신 버전 자동 사용의 차이, 외부 의존성의 가용성에 대해 알아봤다. 
온 세계가 보안 이슈로 떠들썩한데 이런 측면에서도 `검증된` SHA를 pinning하여 사용하는 것이 더 안전하겠다는 생각도 든다.
