2022년 제이펍 출판사 인스타그램 이벤트에서 『좋은 코드, 나쁜 코드』를 받았다. 바로 읽지는 못하고 한동안 책장에 두었다가 2023년이 되어서야 펼쳤다. 늦게 시작한 만큼 무엇이 이해를 도왔는지, 누구에게 권하고 싶은지, 다음 독서에서는 무엇을 바꿀지까지 기록해 둔다.

## 1. 예시를 따라가며 배우는 좋은 코드

이 책에서 가장 좋았던 점은 풍부한 예시 코드다. 코드는 특정 언어에 종속되지 않은 의사 코드로 작성됐지만 문법과 구조가 자바에 가까워 익숙하게 읽을 수 있었다. 개념을 먼저 길게 설명하기보다 실제 코드의 문제를 발견하고 개선하는 흐름을 따라가게 해 추상적인 원칙도 비교적 쉽게 이해됐다.

책은 처음부터 모범 답안만 제시하지 않는다. 먼저 손볼 필요가 있는 코드를 보여주고, 그 코드가 왜 문제가 되는지 도식과 화살표로 짚는다. 이후 어떤 원칙을 적용해야 하는지 설명한 뒤 개선된 코드까지 연결하므로 결과만 보는 것이 아니라 변화의 근거를 함께 따라갈 수 있었다.

| 단계    | 책이 보여주는 것             | 읽으며 얻을 수 있는 것                       |
| ------- | ---------------------------- | -------------------------------------------- |
| 개선 전 | 문제가 숨어 있는 코드와 상황 | 무엇이 불편하고 위험한지 구체적으로 발견한다 |
| 분석    | 도식, 화살표, 관련 이론      | 수정해야 하는 이유를 말로 설명할 수 있다     |
| 개선 후 | 원칙을 반영한 코드           | 전후 차이와 선택의 효과를 비교할 수 있다     |

추상화 계층을 두는 이유, checked exception과 unchecked exception의 차이, 의존성 주입처럼 자주 접하면서도 막상 설명하려면 헷갈리는 주제도 다룬다. 각각의 개념이 코드에서 어떤 문제를 해결하는지 연결해 읽다 보니 개발의 기초 체력을 다시 다지는 기분이 들었다. 결국 좋은 코드를 쓰려면 문법보다 먼저 이런 기본기가 단단해야 한다.

![좋은 코드, 나쁜 코드의 도식과 설명](note-17.jpg)

_책의 도식과 보충 설명은 문제와 개선 방향을 따라가기 쉽게 만든다._

특히 의존성 주입을 설명하는 8장이 재미있었다. 같은 주제를 설명한 글과 책은 많지만 이 책의 설명은 유독 머릿속에 잘 들어왔다. 개념을 분리해서 정의하는 데 그치지 않고 적절한 예시 코드로 필요성과 효과를 함께 보여준 덕분이라고 생각한다.

개발자 사이에서 의견이 갈릴 만한 주제를 다루는 방식도 편안했다. 저자는 자신의 관점을 밝히고 그 판단을 지지하는 근거를 제시하지만, 그 선택이 언제나 유일한 정답이라고 밀어붙이지 않는다. 다른 관점이 성립할 수 있음을 인정하기 때문에 독자도 원칙을 외우기보다 각 주장의 전제와 맥락을 생각하며 읽게 된다.

읽는 동안 여러 개발 서적의 핵심 튜토리얼을 한데 모아 놓았다는 느낌도 받았다. 『클린 코드』나 『오브젝트』와 겹치는 내용이 있지만 지나치게 깊은 곳까지 내려가기보다 지금 알아야 할 내용을 간결하게 정리한다. 마지막 장의 테스트 코드 이야기를 읽고는 관련 책을 더 찾아보고 싶어졌는데, 설명이 모자라서가 아니라 테스트 코드를 제대로 작성하는 일이 왜 중요한지 맛보기로 잘 보여주었기 때문이다.

## 2. 누구에게 잘 맞는 책인가

연차만 기준으로 삼는다면 1~2년 차 개발자부터 읽기 좋다고 생각한다. 이제 막 개발을 시작했거나 아직 다양한 형태의 코드를 다뤄보지 않았다면 책에 등장하는 문제 상황이 충분히 와닿지 않을 수도 있다. 물론 연차보다 어떤 코드를 경험했는지가 더 중요하므로 이는 어디까지나 내 경험을 바탕으로 한 기준이다.

이미 작성된 코드를 계속 다듬거나 리팩터링하는 사람에게도 잘 맞는다. 책은 개선된 결과만 보여주지 않고 그 변경이 필요한 이유를 꾸준히 설명한다. 이를 따라가다 보면 내가 작성한 코드와 앞으로 수정할 코드에 대해 선택의 근거를 말하는 힘을 기를 수 있다.

| 독자                            | 추천하는 이유                                      | 읽을 때 참고할 점                                         |
| ------------------------------- | -------------------------------------------------- | --------------------------------------------------------- |
| 1~2년 차 개발자                 | 여러 코드 개선 상황을 한 번에 접할 수 있다         | 비슷한 경험이 없다면 일부 사례가 바로 와닿지 않을 수 있다 |
| 리팩터링을 자주 하는 개발자     | 변경 전후와 판단 근거를 함께 살펴볼 수 있다        | 책의 답을 그대로 적용하기보다 현재 제약과 비교해야 한다   |
| 객체지향 설계를 사용하는 개발자 | 객체의 책임과 의존성을 다루는 내용이 자주 등장한다 | 객체지향 맥락이 낯설다면 일부 예시가 덜 직접적일 수 있다  |

큰 원칙 사이에 숨어 있는 작은 팁도 많다. 예시 코드를 읽다가 지금 내가 작성한 코드에 바로 적용할 부분을 발견할 수 있고, 실제로 작업하던 코드를 다시 열어보고 싶어지기도 한다. 책에서 배운 내용을 현재 코드와 연결하는 순간 이 책의 장점이 가장 선명해진다.

---

## 3. 필기하며 읽은 방식

아이패드에 필기하면서 읽었다. 눈으로만 읽었다면 금세 사라졌을 내용도 기록으로 남았고, 필기를 다시 보면서 처음 읽을 때는 지나쳤던 생각을 이어갈 수 있었다. 모든 문장을 옮기기보다 잘 모르거나 한 번 더 이해해야 할 부분에 집중해 적은 것도 도움이 됐다.

| 읽는 방식                 | 장점                                                  | 감수할 점                                         |
| ------------------------- | ----------------------------------------------------- | ------------------------------------------------- |
| 눈으로 읽기               | 빠르게 전체 흐름을 훑을 수 있다                       | 기억이 쉽게 흐려지고 생각을 되짚기 어렵다         |
| 필기하며 읽기             | 중요한 내용을 골라 이해하고 다시 살펴볼 자료가 남는다 | 독서 속도가 느려지고 모든 내용을 기록할 수는 없다 |
| 예제 코드를 직접 입력하기 | 코드가 바뀌는 과정과 결과를 손으로 확인할 수 있다     | 가장 많은 시간과 집중력이 필요하다                |

필기는 읽는 속도를 꽤 떨어뜨렸지만 이 책을 읽는 목적은 완독 목록을 빠르게 늘리는 데 있지 않았다. 내가 작성하는 코드를 조금이라도 더 나아지게 만들기 위한 독서라면 속도보다 이해와 적용에 시간을 쓰는 편이 맞다. 느리게 읽더라도 다시 꺼내 볼 자료가 남았다는 점에서 만족스러운 방법이었다.

---

## 4. 다음에는 코드를 직접 입력해 볼 생각이다

아쉬운 점은 처음부터 예제 코드를 직접 작성해 볼 생각을 하지 못했다는 것이다. 마지막 장을 읽을 무렵에야 책의 코드를 따라 입력하고 변경 전과 후가 실제로 어떻게 달라지는지 확인했다. 손으로 필기할 때보다 코드의 변화가 더 선명하게 느껴졌고 배우는 양도 많았다.

한 번 읽은 책은 보통 다시 읽는 편이다. 다음 독서에서는 설명을 읽고 메모하는 데서 멈추지 않고 주요 예제 코드를 직접 작성하면서 개선 과정을 재현해 볼 생각이다. 어떤 수정이 동작과 구조를 어떻게 바꾸는지 확인하면 책에서 제시한 근거도 더 오래 남을 것이다.

---

## 5. 결국 좋은 코드란 무엇인가

이 책을 읽던 날 만난 개발자가 좋은 코드와 나쁜 코드는 무엇이냐고 물었다. 우선 내가 작성한 코드는 나쁜 코드라고 웃으며 답했지만, 조금 더 생각해 보니 좋은 코드는 선택의 근거가 단단한 코드에 가깝다는 결론이 남았다. 구현이 짧거나 특정 원칙을 따랐다는 사실만으로 좋은 코드가 되지는 않는다.

책에서도 서로 대립하는 여러 의견을 함께 다룬다. 모든 상황에 통하는 하나의 답은 없고 주어진 맥락에 적합한 선택이 있을 뿐이다. 코드가 놓인 환경과 제약을 이해하고 그에 맞는 이유를 세운 뒤 작성했다면 좋은 코드라고 부를 수 있지 않을까.

어떤 해법 하나로 모든 문제를 해결할 수 없다는 오래된 결론으로 다시 돌아오게 된다. 은탄환은 없지만 그래서 선택의 근거가 더 중요해진다. 오랫동안 반복되는 말에는 그만한 이유가 있다.

---

## 6. 읽고 나서 남긴 체크리스트

- [ ] 코드를 고칠 때 결과뿐 아니라 변경해야 하는 이유도 설명한다.
- [ ] 추상화 계층, 예외 종류, 의존성 방향을 선택한 근거를 확인한다.
- [ ] 하나의 원칙을 모든 상황에 적용하기 전에 현재 코드의 맥락과 제약을 살핀다.
- [ ] 예시에서 발견한 작은 개선점을 지금 작성 중인 코드에도 적용할 수 있는지 찾아본다.
- [ ] 테스트 코드를 더 깊이 공부할 다음 책이나 자료를 정한다.
- [ ] 다시 읽을 때는 주요 예제 코드를 직접 입력하고 개선 전후를 비교한다.
