## 세줄 요약

1. Pyroscope에서 `gzip.Writer` 반복 생성과 캐시 데이터 복사를 allocation 병목으로 찾았다.
2. `sync.Pool`을 이용한 writer 재사용과 한 줄짜리 복사 제거를 각각 PR로 배포했다.
3. 카나리 기준 요청당 할당량은 37%, CPU는 11% 줄었다. 더 공격적인 세 번째 최적화는 GC 비용을 키워 롤백했다.

<br/>


운영 중인 Go 서버의 Pyroscope를 살펴보다가 상대적으로 넓은 allocation 경로 두 개를 발견했다.
기능상 문제나 CPU가 부족한 상황도 아니었지만 요청마다 새로 만들고 버리는 메모리가 많았다.

첫 번째는 gzip writer를 매번 새로 만드는 부분이었고,
두 번째는 로컬 캐시에 이미 있는 JSON 바이트를 조회할 때마다 통째로 복사하는 코드였다.

쉽게 말하면 이미 만든 것을 **다시 만들고**, 읽기 전용 데이터를 **매번 복사**하는 것이 문제였다.

## Pyroscope에서 찾은 두 개의 할당 경로

운영서버의 프로파일에서 CPU와 메모리 할당을 함께 확인했다.

| 경로                                   |                             관찰 결과 |
| -------------------------------------- | ------------------------------------: |
| `compress/flate.NewWriter` 계열        |               전체 누적 할당의 40.67% |
| 캐시 hit의 `[]byte` 복사               | 30분 누적 1.11TB, 전체 할당의 약 3.1% |
| `RedisLineitemIndex.RetrieveLineitems` |                     전체 CPU의 22.37% |

여기서 `1.11TB`는 서버가 한 번에 점유한 메모리는 아니고, `alloc_space`는 조회 구간에 할당된 메모리를 모두 더한 값으로 생성 직후 GC로 회수된 바이트도 포함한다.
현재 살아 있는 메모리를 보려면 `inuse_space`를 봐야 한다. 두 값을 구분하지 않으면 “메모리를 1TB 썼다”는 잘못된 결론에 도달하기 쉽다.

## gzip writer 재사용

기존 코드는 gzip 요청을 보낼 때마다 새 writer를 만들었다.
이미지가 조금 구리지만 왼쪽은 요청마다 gzip 압축기를 새로 만들고 버리는, 오른쪽은 필요한 동안 빌려 쓴 뒤 되돌려놓는 모습이다.
![요청마다 gzip writer를 새로 만드는 방식과 하나를 재사용하는 방식](gzip-writer-reuse.jpg)
### as-is
```go
b := &bytes.Buffer{}
gzWriter := gzip.NewWriter(b)

if _, err := gzWriter.Write(postBody); err != nil {
    return nil, err
}
_ = gzWriter.Close()
```

`gzip.NewWriter` 내부의 `flate.Writer`는 압축에 필요한 큰 버퍼와 자료구조를 만들고 시작하는데 요청이 많아질수록 동일한 준비를 반복하고, 사용이 끝난 객체는 다시 GC의 회수 대상이 된다.

### to-be
표준 라이브러리의 `sync.Pool`과 `gzip.Writer.Reset`을 사용해 writer를 재사용했다.
```go
var gzipWriterPool = sync.Pool{
    New: func() any {
        return gzip.NewWriter(io.Discard)
    },
}

func writeGzip(dst io.Writer, src []byte) error {
    w := gzipWriterPool.Get().(*gzip.Writer)
    w.Reset(dst)
    defer func() {
        w.Reset(io.Discard)
        gzipWriterPool.Put(w)
    }()

    if _, err := w.Write(src); err != nil {
        return err
    }
    return w.Close()
}
```

`Reset`은 압축 상태를 새 출력 대상으로 초기화하면서 내부 버퍼는 재사용한다.
pool에 돌려보내기 전 `io.Discard`로 다시 연결해 이전 요청의 buffer를 계속 참조하지 않게 했다.

`sync.Pool`은 GC 과정에서 비워질 수 있다. 그래서 데이터 캐시로는 부적합하지만, 없어져도 다시 만들면 되는 임시 객체를 재사용하는 목적에는 잘 맞는다.

재사용은 이전 요청의 상태가 다음 요청에 섞일 위험을 만든다. 서로 다른 payload를 연속으로 압축한 뒤 각각 독립적으로 복원되는 테스트를 추가하고, race detector도 함께 실행했다.

## 캐시 hit의 바이트 복사 제거

두 번째 병목은 한 줄에 있었다. 로컬 캐시에서 `[]byte`를 찾은 뒤 새로운 backing array를 만들고 전체 데이터를 복사했다.

![캐시 데이터를 매번 복사하는 방식과 읽기 전용으로 공유하는 방식](read-only-cache-bytes.jpg)
_왼쪽은 읽는 사람마다 복사본을 만드는 모습, 오른쪽은 원본을 바꾸지 않고 함께 들여다보는 모습이다._

```go
cachedBytes := cached.([]byte)
result[id] = append([]byte(nil), cachedBytes...)
```

`cached.([]byte)`는 바이트 전체를 복사하지 않는다. backing array의 주소, 길이, 용량으로 이루어진 slice header만 가져온다.

실제 복사는 다음 줄의 `append`에서 발생한다. 시작 slice의 용량이 0이므로 새 backing array를 할당하고, `cachedBytes`의 모든 원소를 옮긴다.

복사는 안전한 기본값이다. 반환받은 코드가 바이트를 수정해도 캐시 원본은 오염되지 않는다. 문제는 이 함수의 유일한 소비자가 입력을 읽기만 하는 `json.Unmarshal`이었다는 점이다.

새 배열을 만들지 않고 캐시의 backing array를 공유했다.

```go
if cached, found := r.dataCache.Get(id); found {
    // Cached bytes are read-only.
    result[id] = cached.([]byte)
}
```

코드는 한 줄 줄었지만 계약은 더 강해졌다. 반환된 slice의 원소를 수정하면 캐시도 함께 바뀐다. 짧은 주석으로 read-only 조건을 남긴 이유다.

호출 경로를 확인해 `json.Unmarshal`이 입력을 변경하지 않는지 검증했다. 테스트에서는 반환값이 캐시와 같은 backing array를 가리키는지도 확인했다.

공개 API였다면 이 최적화를 선택하지 않았을 것이다. 그러나 private 함수이고 소비자가 하나뿐이라 읽기 전용 조건을 좁게 유지할 수 있었다.

## 카나리에서 실제 효과 확인하기

두 PR은 각각 merge한 뒤 함께 카나리 배포했다. 10시 30분부터 일부 pod에 적용했고, 10시 58분에 전체 배포로 전환했다.

비교에는 10시 35분부터 10시 50분까지 동시에 트래픽을 받은 구버전과 신버전을 사용했다. 두 버전의 APM 요청 표본 차이는 약 3%였다.

pod 수나 요청 수가 다른 상태에서 누적 CPU만 비교하면 트래픽 차이를 성능 개선으로 오해할 수 있다. 그래서 경로별 변화와 함께 `RequestBid` 표본당 할당량과 CPU를 계산했다.

| 지표                       |        변화 |
| -------------------------- | ----------: |
| `sendOtherRequests` 할당량 | 약 94% 감소 |
| `loadLineitemData` 할당량  | 약 90% 감소 |
| 요청당 전체 할당량         | 약 37% 감소 |
| 요청당 전체 CPU            | 약 11% 감소 |

`compress/flate.NewWriter`는 신버전의 주요 allocation 경로에서 사라졌다. `loadLineitemData`의 누적 할당 비중도 3.55%에서 0.57%로 줄었다.

반면 초당 생성되는 heap object 수는 눈에 띄게 줄지 않았다. 이번에 없앤 것은 수많은 작은 객체보다 압축 버퍼와 JSON backing array처럼 비교적 큰 객체였기 때문이다.

객체 1,000개 중 큰 객체 10개만 없애면 개수는 1% 줄지만 바이트는 크게 줄 수 있다. `Heap Memory Allocated`가 내려가고 `Heap Objects Allocated`가 비슷했던 이유다.

writer를 pool에 보관하는 비용도 있었다. gzip 관련 in-use 비중은 2.24%에서 6.15%로 늘었다. 배포 후 전체 live heap은 약 85.3MiB였고, 당시 2GiB 제한의 약 4.2% 수준이었다.

GC pause p95도 2.15ms로 안정적이었다. 할당 감소와 상주 메모리 증가를 함께 보고, 현재 운영 여유 안에서 받아들일 수 있는 교환이라고 판단했다.

## 빠른 벤치마크가 운영 성능을 보장하지는 않았다

두 변경 뒤에는 더 큰 CPU 병목인 반복 `json.Unmarshal`도 없애보고 싶었다. 캐시에 JSON 바이트 대신 변환된 Go DTO를 저장하는 PR을 추가로 만들었다.

로컬 벤치마크는 매우 좋았다. 실행 시간은 79.9%, 할당 바이트는 49.1%, 할당 횟수는 58.6% 줄었다.

프로덕션에서도 목표 경로는 개선됐다. `encoding/json.Unmarshal` CPU는 약 68%, `RetrieveLineitems` CPU는 약 65% 감소했다.

하지만 전체 서비스는 빨라지지 않았다. 비슷한 트래픽 구간을 비교했을 때 요청당 총 CPU는 약 29~30%, 평균 지연시간은 16~27% 늘었다.

원인은 GC였다. raw JSON `[]byte`는 큰 바이트 배열 하나지만, 변환된 DTO는 문자열과 slice, 중첩 구조체가 연결된 많은 객체다.

`loadLineitemData` 아래의 live object 비중은 14.33%에서 46.14%로 늘었다. GC가 따라가며 검사해야 할 포인터가 많아지면서 `runtime.gcDrain` 비중도 6.43%에서 14.36%로 올랐다.

JSON 변환에서 아낀 CPU가 GC mark와 scan으로 이동한 셈이다. 이 변경은 롤백했고, 앞의 두 PR만 유지했다.

이 경험 때문에 이번 글의 성능 개선 PR을 두 개라고 적었다. 세 번째 PR은 특정 함수와 벤치마크를 개선했지만, 서비스 전체 성능을 개선하지는 못했다.

## 마무리

![adn-grafana](adn-grafana.jpg)

이번 작업에서 가장 효과가 좋았던 변경은 새로운 캐시나 복잡한 알고리즘이 아니었다. 이미 만든 writer를 재사용하고, 읽기 전용 데이터를 다시 복사하지 않는 일이었다.

프로파일은 어디가 비싼지 알려줬고, 카나리는 그 비용을 없앤 결과가 서비스 전체에도 남는지 확인해줬다. 둘 중 하나만 봤다면 세 번째 시도를 성공으로 착각했을 가능성이 크다.

앞으로 Go 서버의 메모리 성능을 볼 때는 할당 바이트만 보지 않으려 한다. 살아 있는 바이트와 객체 수, GC CPU, 요청당 CPU, 지연시간까지 같이 봐야 최적화가 끝난다.
