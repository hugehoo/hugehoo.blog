## 들어가면서 

레거시 서버를 셧다운 하기로 마음 먹었다면 어떤 작업을 준비해야할까. 냅다 해당 서버 파드를 모두 내리면 될까? 기존에 서버를 호출하던 프론트엔드나 클라이언트 측 정리는 어떻게 해야할지도 함께 고민해야한다. 
이미 레거시 서버가 되어버린 탓에 라이브중인 프론트엔드, 클라이언트 호출은 없었지만 레거시 SDK으로 부터의 API call은 APM에 여전히 남아 있었다. 레거시 SDK가 호출하던 API에 일괄적으로 204 no-content 응답을 내려줘도 문제없다는 확인을 받은 후, 선셋 예정인 서버로 들어오는 요청을 모두 gateway로 라우팅하기로 하고, gateway에서 일괄적으로 204 응답을 주기로 결정했다. 사실 원래부터 게이트웨이를 통해 요청이 들어와야 맞지만, 레거시 특성상.. 유노?

처음에는 게이트웨이에 204 처리 코드와 신규 라우트를 추가한 후, 기존 서비스의 라우트를 지우는 정도로 작업을 산정했다. 다만 배포 순서를 검토하다가 **같은 호스트와 경로를 가진 라우트가 동시에 존재하면 어느 쪽이 요청을 받는 걸까**라는 의문이 생겼다.

이 질문에 따라 실제 트래픽의 목적지를 바꾸는 작업과 라우트 설정을 관리하는 저장소를 옮기는 작업을 분리했고, 최종적으로는 네 단계로 배포할 수 있도록 PR을 나눴다.

## istio gateway와 api gateway

먼저 우리 시스템에서 사용하는 두 가지 게이트웨이를 구분해보면, **Istio ingress**는 외부 요청을 받는 Envoy 프록시이고 **api-gateway**는 요청을 처리하는 별도의 HTTP 애플리케이션으로 흔히 msa에서 말하는 중앙 gateway로 볼 수 있다. (여기서 말하는 `api-gateway`는 Istio의 `Gateway` 리소스 이름과는 별개임)

### 기존
```text
클라이언트: https://api.example.com/v1/retired/items
    ↓
Istio ingress (Envoy)
    ↓
legacy-service
    ↓
기존 조회 응답
```

### 변경
변경 후에는 클라이언트의 URL을 유지하면서 ingress 뒤의 목적지를 바꾼다.

```text
클라이언트: https://api.example.com/v1/retired/items
    ↓
Istio ingress (Envoy)
    ↓
(라우팅 변경)
    ↓
api-gateway
    ↓
HTTP 204 No Content, 빈 본문
```

`VirtualService`는 Envoy가 요청을 어디로 보낼지 결정할 때 사용할 규칙으로 기존 규칙을 단순화해서 표현하면 아래와 같다.

```yaml
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: legacy-api-routes
  namespace: legacy
spec:
  hosts:
    - api.example.com
  gateways:
    - istio-system/public-ingress
  http:
    - name: retired-api
      match:
        - uri:
            prefix: /v1/retired/
      route:
        - destination:
            host: legacy-service.legacy.svc.cluster.local # <- ingress가 요청을 전달하던 내부 서비스 주소
            port:
              number: 8080
```

`hosts`는 클라이언트가 요청하는 호스트, `destination.host`는 실제로 요청을 받을 내부 서비스다. 이 둘을 구분하면 외부 URL을 바꾸지 않고 내부 목적지만 교체할 수 있다. 이번 케이스에선 legacy sdk가 호출하던 주소를 변경할 수 없으니 destination.host를 **legacy server -> api gateway** 로 바꿔치기하면 된다. 

## Istio 설정은 어디에 있나?

우리 회사는 각 마이크로 서비스 레포지토리의 Helm values가 라우팅 설정을 관리하고 있다.
공용 Helm chart가 values를 읽어 `VirtualService`를 렌더링하고 배포 과정에서 해당 리소스를 클러스터에 적용하는 구조로 볼 수 있다.

```text
서비스 저장소의 release/values.prod.yaml
    ↓ Helm chart로 렌더링
Kubernetes의 VirtualService 리소스
    ↓ istiod가 설정을 구성·전파
ingress Envoy의 실제 라우트
```

따라서 게이트웨이 애플리케이션에 204 핸들러를 추가하는 일과 ingress의 목적지를 게이트웨이로 바꾸는 일은 별개다. 핸들러만 바꾸면 ingress는 계속 기존 서비스로 요청을 보낸다. 라우팅을 바꾸려면 Helm values도 수정해야 한다.

## 새 규칙을 추가한다고 기존 규칙을 오버라이드 하지 않는다

처음 생각했던 방식으로 게이트웨이를 먼저 배포하면 클러스터에는 다음 두 규칙이 함께 존재한다.

```text
legacy-api-routes
  api.example.com + /v1/retired/ → legacy-service

gateway-retired-api-routes
  api.example.com + /v1/retired/ → api-gateway
```

Istio는 ingress Gateway에 연결된 여러 `VirtualService`가 같은 호스트를 사용하면 라우트 규칙을 병합할 수 있다. 하지만 병합된 규칙의 평가 순서를 임의로 기대해서는 안 된다.

하나의 `VirtualService` 안에서는 `http` 규칙을 위에서부터 평가한다. [공식 문서의 Routing rule precedence](https://istio.io/latest/docs/concepts/traffic-management/#routing-rule-precedence)에도 이 순서가 설명돼 있다.

반면 [여러 VirtualService를 병합할 때의 문서](https://istio.io/latest/docs/ops/best-practices/traffic-management/#split-virtual-services)는 리소스 간 평가 순서를 **the cross-resource order is UNDEFINED**라고 명시한다. 새로 배포한 리소스가 기존 리소스보다 우선한다고 보장하지 않는다.

여기서 다루는 병합은 ingress Gateway에 바인딩된 `VirtualService`에 대한 동작이다. 같은 호스트를 여러 리소스에 선언하는 방식을 sidecar의 mesh 라우팅에도 그대로 적용할 수 있는건 아니다.

그럼 기존 rule부터 지우면 어떨까? 새 rule이 준비되기 전까지 라우트가 비는 구간이 생길 수 있다. 원하는 것은 게이트웨이가 의도적으로 반환하는 204인데, ingress가 라우트를 찾지 못하면 그대로 404가 발생할 수 있다.

## 트래픽 전환과 설정 관리 주체 이전을 나누기

1. 기존 URL의 요청을 게이트웨이로 보내 204 No-Content를 반환한다.
2. 기존 서비스를 셧다운해도 라우트가 유지되도록 istio values 설정을 api-gateway 레포지토리로 옮긴다.

첫 번째 목표만 필요하다면 기존 `VirtualService`의 목적지를 변경하는 것으로 끝낼 수 있지만 rule을 계속 기존 서비스에 남겨두면, 추후에 해당 서버를 셧다운 시 종료된 API를 처리하는 라우트까지 사라질 수 있다. 그래서 설정을 관리하는 주체도 함께 옮겨줘야 했다.

| 상태  | 기존 서비스가 관리하는 VS | 게이트웨이가 관리하는 VS | 요청의 목적지                           |
| ----- | ------------------------- | ------------------------ | --------------------------------------- |
| 시작  | 기존 서비스로 전달        | 없음                     | 기존 서비스                             |
| 1단계 | 기존 서비스로 전달        | 없음                     | 기존 서비스, 게이트웨이는 204 처리 준비 |
| 2단계 | 게이트웨이로 전달         | 없음                     | 게이트웨이                              |
| 3단계 | 게이트웨이로 전달         | 게이트웨이로 전달        | 어느 규칙을 골라도 게이트웨이           |
| 4단계 | 없음                      | 게이트웨이로 전달        | 게이트웨이                              |

이 순서는 **서로 다른 목적지를 가진 중복 규칙을 만들지 않는다.** 두 규칙이 잠시 겹치는 3단계에서는 어느 쪽이 선택돼도 같은 동작을 하도록 만든다.

### 1단계. 게이트웨이의 204 처리 코드만 먼저 배포한다

먼저 게이트웨이에 종료된 API의 응답을 준비한다. 아래는 공통 prefix 아래의 요청을 처리하도록 단순화한 Echo v4 예시다.

```go
e.Any("/v1/retired/*", func(c echo.Context) error {
    return c.NoContent(http.StatusNoContent)
})
```

실제 변경에서는 기존 API 경로들을 각각 등록하고, 더 이상 기존 서비스를 호출하지 않도록 프록시 의존성도 제거했다. 위 예시처럼 prefix로 묶는다면 그 아래에 종료 대상이 아닌 API가 섞여 있지 않은지 먼저 확인해야 한다.

회귀 테스트에서는 기존 경로들의 GET과 POST가 빈 본문의 204를 반환하는지 확인했다. GET 핸들러만 등록하면 다른 메서드는 프레임워크가 405로 처리할 수 있기 때문에, ingress의 메서드 매칭 조건과 애플리케이션의 등록 범위를 함께 봤다.

이 단계에서는 외부 URL의 ingress 라우팅을 바꾸지 않는다. 새 코드가 준비된 모든 게이트웨이 인스턴스에서 기존 서비스를 호출하지 않고 204를 반환하는지 확인한다. ingress에서 해당 Kubernetes Service에 접근할 수 있는지와 포트·접근 정책도 확인 대상이다.

### 2단계. 기존 VirtualService의 목적지만 바꾼다

게이트웨이가 준비되면 기존 서비스 저장소에서 라우트의 목적지만 수정한다. 리소스의 이름, 네임스페이스, 호스트와 경로 조건은 유지한다.

```diff
 route:
   - destination:
-      host: legacy-service.legacy.svc.cluster.local
+      host: api-gateway.edge.svc.cluster.local
       port:
         number: 8080
```

네임스페이스가 다른 서비스로 보낼 때는 FQDN을 사용했다. Istio는 짧은 서비스명을 규칙이 정의된 네임스페이스 기준으로 해석하기 때문이다. 게이트웨이 쪽으로 설정을 옮긴 뒤에도 같은 서비스를 가리키게 만들려면 목적지를 명확히 적는 편이 낫다. [VirtualService의 destination 설명](https://istio.io/latest/docs/reference/config/networking/virtual-service/#Destination)에 이 해석 방식이 나와 있다.

여기서는 새 `VirtualService`를 추가하지 않는다. 기존 규칙 하나가 가리키는 목적지만 교체하므로, 서로 다른 목적지를 가진 두 규칙 사이의 평가 순서를 고민할 필요가 없다.

다만 설정이 모든 ingress에 동시에 적용되는 것은 아니다. 전파 중에는 기존 응답과 204가 함께 관찰될 수 있으므로 이 단계에서도 기존 서비스를 유지한다. 새 목적지를 사용할 준비를 끝낸 뒤 라우트를 바꾸고, 전파를 확인한 다음 이전 대상을 정리하는 순서다. [Istio의 라우트 재설정 가이드](https://istio.io/latest/docs/ops/best-practices/traffic-management/#avoid-503-errors-while-reconfiguring-service-routes)도 설정 변경 중 목적지의 준비 상태와 전파 순서를 주의하도록 설명한다.

### 3단계. 게이트웨이 저장소에도 같은 규칙을 추가한다

기존 규칙을 통해 요청이 게이트웨이로 전달되는 것을 확인한 뒤, 게이트웨이 저장소에도 라우트를 등록한다. 앞에서 본 YAML과 비교하면 리소스를 관리할 이름·네임스페이스와 목적지가 달라진다.

```yaml
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata:
  name: gateway-retired-api-routes
  namespace: edge
spec:
  hosts:
    - api.example.com
  gateways:
    - istio-system/public-ingress
  http:
    - name: retired-api
      match:
        - uri:
            prefix: /v1/retired/
      route:
        - destination:
            host: api-gateway.edge.svc.cluster.local
            port:
              number: 8080
```

이제 같은 호스트와 경로를 가진 두 규칙이 공존한다. 하지만 2단계에서 기존 규칙도 게이트웨이를 가리키도록 바꿨으므로 어느 규칙이 먼저 평가돼도 목적지가 같다.

이때 목적지 주소만 같으면 충분한 것은 아니다. 실제 설정에서는 Gateway 바인딩, 리소스 가시성, match 조건, rewrite, 헤더 처리, timeout, 재시도와 CORS 정책도 비교해야 한다. 요청이나 응답을 바꾸는 설정이 다르면 선택된 규칙에 따라 동작이 달라질 수 있다. 위 YAML에서는 설명을 위해 이런 정책을 생략했다.

### 4단계. 기존 서비스 저장소에서 라우트를 제거한다

새 규칙이 ingress에 반영된 것을 확인하면 기존 서비스 저장소의 라우트 설정을 제거한다. 최종적으로는 게이트웨이 저장소에서 배포하는 규칙만 남는다.

Helm이나 GitOps가 관리하는 환경에서는 클러스터에서 리소스만 수동 삭제해 끝내지 않는다. 배포 설정의 원본도 바꿔야 다음 배포나 동기화 과정에서 기존 규칙이 다시 생성되지 않는다.

이 단계가 끝났다고 기존 서비스의 모든 리소스를 곧바로 삭제하는 것은 아니다. 외부 HTTP 요청 이외의 내부 호출이나 배치 작업도 있는지 확인해야 한다. 여기서 분리한 작업 범위는 해당 ingress 라우트의 전환과 관리 주체 이전까지다.


## 마무리

최종적으로 변경 사항을 검토하고 아래처럼 네 개의 PR로 분리하여 적용했다.

| PR  | 변경 범위                                                  | 다음 단계로 진행할 조건                                           |
| --- | ---------------------------------------------------------- | ----------------------------------------------------------------- |
| 1   | 게이트웨이의 204 처리 코드와 불필요한 upstream 의존성 제거 | 게이트웨이의 준비 상태와 직접 요청의 204 확인                     |
| 2   | 기존 VirtualService의 목적지만 변경                        | 실제 ingress의 목적지, 외부 요청의 204, 기존 API 트래픽 감소 확인 |
| 3   | 게이트웨이 저장소에 동일한 라우트 추가                     | 공존하는 두 규칙의 동작과 ingress 반영 상태 확인                  |
| 4   | 기존 서비스 저장소의 라우트 제거                           | 새 규칙만 남은 상태와 실제 요청 처리 경로 확인                    |


이번 케이스는 레거시 sdk에서 서버 api 호출을 제어하지 못했기 때문에, 서버 단에서 라우트 변경을 고려한 후 셧다운을 진행해야 했다.
몇 줄의 라우팅 설정과 짧은 핸들러 변경으로 끝날 줄 알았으나 배포 단위로 나눠보니 최종 설정뿐 아니라 그 사이에 잠시 존재할 상태들도 설명할 수 있어야 했다.
