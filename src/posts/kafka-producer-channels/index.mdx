Go 서버의 힙 프로파일을 보다가 Kafka 프로듀서를 만드는 두 줄에서 눈이 멈췄다. 사용 중인 라이브러리는 `confluent-kafka-go` v2.12.0이었다. 기본 설정으로 프로듀서 하나를 만들면 다음 두 채널에 각각 100만 슬롯이 생긴다.

```go
p.events = make(chan Event, eventsChanSize)
p.produceChannel = make(chan *Message, produceChannelSize)
```

두 번째 줄은 메시지 본문이 들어오기 전부터 메모리를 쓴다. 64비트 환경에서 포인터 하나가 8바이트이니 빈 채널도 배열 크기만 약 7.6 MiB다. 우리 서버는 프로듀서를 두 개 쓰니까 15.3 MiB다. 그런데 이걸 한 슬롯으로 줄이면 브로커가 잠깐 느려졌을 때 메시지를 딱 하나만 받아줄까? 답은 **애플리케이션이 어느 API로 발행하느냐**에 달려 있었다. [프로듀서 초기화 코드](https://github.com/confluentinc/confluent-kafka-go/blob/v2.12.0/kafka/producer.go#L537)

## 우리 메시지는 어느 채널을 지날까?

`ProduceChannel()`은 애플리케이션이 메시지를 **써 넣는** 채널이다. `p.ProduceChannel() <- msg`처럼 쓰면 SDK의 고루틴이 메시지를 꺼내 내부 전송 큐로 넘긴다. 이 방식에선 Go 채널이 꽉 차면 빈자리가 생길 때까지 보내는 쪽이 기다린다. 이 채널 방식은 v2.12.0에서 deprecated 상태다.

우리 코드에서 실제로 호출하는 메서드는 `Produce()`였다. 두 방식은 첫 단계부터 경로가 다르다.

```text
p.ProduceChannel() <- msg   → Go 채널 → SDK 고루틴 → librdkafka 전송 큐
p.Produce(msg, deliveryCh)                        → librdkafka 전송 큐
```

`librdkafka`는 Go 클라이언트가 내부에서 사용하는 C 라이브러리다. `Produce()`가 `nil`을 반환하면 이 라이브러리가 메시지를 큐에 받아들였다는 뜻이다. 브로커 전송은 비동기로 진행한다. 이때 내부 큐가 꽉 차면 `Produce()` 호출에서 바로 `ErrQueueFull`을 받을 수 있다. [Produce와 채널 소비 루프](https://github.com/confluentinc/confluent-kafka-go/blob/v2.12.0/kafka/producer.go#L298)

그럼 전송 결과는 어디서 받을까? `Produce(msg, deliveryCh)`처럼 채널을 넘겼다면 그 채널로 delivery report가 온다. 애플리케이션은 반환된 메시지의 `TopicPartition.Error`를 읽어 성공과 실패를 구분한다. 우리 코드는 이 경로에서 발행 지연도 측정한다.

남은 하나인 `Events()`는 반대 방향이다. SDK가 여기에 이벤트를 **보내고** 애플리케이션이 **읽는다**. 우리 서버에서는 collector가 여기서 브로커 오류와 5초 주기의 통계를 읽는다. 별도 delivery 채널을 넘기지 않고 `Produce(msg, nil)`로 발행하면 기본 설정에서는 전송 결과도 `Events()`로 온다. 발행 코드와 함께 두 번째 인자까지 확인해야 어떤 채널에 부하가 걸리는지 알 수 있다. [SDK의 delivery 채널 선택](https://github.com/confluentinc/confluent-kafka-go/blob/v2.12.0/kafka/event.go#L229)

## 발행 채널이 한 슬롯인데 256건이 들어갔다

같은 SDK와 추적 래퍼를 쓰는 로컬 모의 브로커에서 `go.produce.channel.size`만 100만과 1로 바꿔 봤다. 브로커를 중단하고, 큐가 차는 순간을 확인하기 위해 librdkafka의 내부 큐 상한은 양쪽 모두 256건으로 맞췄다. 발행은 운영 코드와 똑같이 `Produce()`를 호출했다.

| 측정 항목 | 100만 슬롯 | 1슬롯 |
| --- | ---: | ---: |
| 브로커 중단 후 첫 ErrQueueFull 전까지 받아들인 메시지 수 (프로듀서당) | 256 | 256 |
| 복구 후 순서대로 소비한 메시지 수 (두 프로듀서 합계) | 6,000 / 6,000 | 6,000 / 6,000 |
| 두 프로듀서 생성 전후의 Go 힙 증가량 | 45.80 MiB | 30.52 MiB |

한 슬롯으로 줄여도 257번째 메시지에서 큐 포화 오류가 났다. 우리가 채운 큐가 어디인지 숫자로도 드러났다. 두 프로듀서에서 줄어든 Go 힙도 약 15.3 MiB로, 처음에 포인터 크기로 계산한 값과 맞았다. 이 값은 로컬에서 GC 후 측정한 힙 차이다.

## 이벤트 채널도 같이 줄일 수 있을까?

이번에는 발행 채널을 1로 고정하고 `go.events.channel.size`를 100만에서 1,000으로 줄였다. collector가 계속 이벤트를 읽을 때는 두 설정 모두 10만 건을 발행하고 순서대로 읽었다. 차이는 **읽는 쪽을 멈췄을 때** 나타났다.

운영에서 5초인 통계 주기를 실험에서는 10ms로 당겼다. 이벤트를 읽지 않고 약 1,000개가 쌓일 때까지 기다린 다음, 별도 delivery 채널을 지정해 메시지 하나를 보냈다. 기본값에선 2초 안에 전송 결과를 받았다. 1,000슬롯이 가득 찬 경우에는 2초가 지나도 결과가 오지 않았다. 이벤트 소비를 재개하자 기다리던 결과가 도착했고, 종료 시 미전송 건수는 0이었다.

결과를 받을 채널을 따로 줬는데도 왜 기다렸을까? SDK에서는 같은 poller가 librdkafka의 이벤트를 꺼내 종류에 맞는 Go 채널로 보낸다. 통계 이벤트를 `Events()`에 보내는 순간 막히면 뒤에 있는 delivery report도 꺼내지 못한다. 실험에서 늦어진 시점은 애플리케이션이 결과를 받은 때다. 브로커가 메시지를 기록한 시각은 이 관측만으로 알 수 없다. [SDK poller의 채널 전송 코드](https://github.com/confluentinc/confluent-kafka-go/blob/v2.12.0/kafka/event.go#L293)

그래서 이번 변경에서는 발행 채널만 1로 줄였다. 이쪽은 호출부에서 `Produce()`를 쓴다는 사실만으로도 100만 슬롯이 비어 있는 이유를 설명할 수 있었다. 이벤트 채널의 적정 크기를 정하려면 질문이 하나 더 필요하다. **브로커 오류가 몰릴 때 collector가 따라잡기까지 이벤트가 얼마나 쌓이는가?**
