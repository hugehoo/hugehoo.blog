## CS가 몰리는 상황을 먼저 알아챌 수 없을까

광고에 참여했는데 보상을 받지 못했다는 문의가 특정 캠페인에 몰린다면, 개별 문의를 처리하는 것과 별개로 공통된 문제가 있는지 확인할 필요가 있다. 비슷한 내용을 여러 번 읽고 나서야 상황을 알아채기보다는, 문의가 늘어나는 시점에 어떤 내용이 많은지 함께 알 수 있으면 좋겠다고 생각했다.

그렇다고 문의가 들어올 때마다 Slack 알림을 보내고 싶지는 않았다. 문의가 많아질수록 알림도 많아지고, 결국 운영자가 다시 내용을 모아 봐야 하기 때문이다. 캠페인별로 문의를 집계하고 일정 기준을 넘었을 때 주요 내용을 정리해 알려주는 방식으로 접근했다.

## Jev를 고려한 이유

문의 내용을 분류할 방법을 찾다가 TypeSafe의 Jev를 고려하게 됐다. Jev는 텍스트 같은 비정형 입력을 받아 미리 정의한 선택지 중 하나를 고르고, 각 선택지의 확률과 confidence를 반환하는 모델이다. [Choice 공식 문서](https://docs.typesafe.ai/primitives/choice)에도 고객 문의를 담당 부서로 분류하는 예시가 나온다.

이번 작업에서는 ‘보상 미지급’, ‘지급 지연’, ‘미션 미인식’처럼 유형을 정해두고 문의를 분류하면 됐다. 선택지와 함께 불확실성을 확인할 수 있다는 점이 이 작업에 잘 맞을 것 같았다.

현재 구현은 기존 CS 데이터와 Redis를 이용해 캠페인별 문의 사용자 수를 집계한다. 같은 사용자의 반복 문의는 중복으로 세지 않고, 급증 후보가 생기면 최근 문의 최대 20건을 Jev로 분류해 Slack 알림에 넣는다. 여기서 분류하는 것은 사용자가 주장하는 증상이다. ‘보상 미지급’이 많다는 결과만으로 실제 보상 처리에 장애가 있다고 확정할 수는 없다.

## 연결하고 테스트해봤다

우선 합성 한국어 문의 8건을 만들어 실제 Jev API를 호출했다. 준비한 8건 모두 기대한 유형과 일치했다. 다만 직접 만든 작은 표본이므로, 이 결과를 실제 문의에서도 정확하게 분류한다는 근거로 보기는 어려웠다. API 연결과 기본적인 분류 동작을 확인한 정도다.

주변 로직은 별도로 검증했다. 관련 테스트 174개를 통과했고, 실제 Redis에서도 중복 접수와 데이터 만료, 알림 간격 제한이 동작하는지 확인했다. 과거 문의를 늦게 처리해도 현재 문의량으로 집계하지 않는지, Jev 분류가 실패하거나 오래 걸려도 문의량 알림은 보낼 수 있는지도 테스트했다.

이 과정에서 확인한 것은 구현이 정해둔 조건대로 동작하는지였다. 문의를 얼마나 정확하게 이해하는지, 알림이 운영자의 판단에 도움이 되는지는 다른 검증이 필요했다.

## 아직 부족한 부분

가장 먼저 필요한 것은 실제 문의를 대상으로 한 평가다. 사람이 문의 유형을 분류한 정답 데이터를 만들고, Jev가 어떤 유형을 자주 혼동하는지 확인해야 한다. ‘아직 지급 예정일이 지나지 않았다’는 문의와 ‘지급일이 지났는데 받지 못했다’는 문의를 잘 구분하는지도 살펴볼 필요가 있다.

표본을 고르는 방식에도 한계가 있다. 최근 20건에 특정 유형이 많다고 전체 문의에서도 같은 비중이라고 볼 수는 없다. 고정된 급증 기준 역시 평소 문의가 많은 캠페인과 적은 캠페인에 똑같이 적용해도 되는지 확인이 필요하다.

운영 측면에서는 외부로 보내는 본문에 개인정보가 남지 않는지 점검해야 하고, Redis 장애나 데이터 유실로 감지를 놓칠 가능성도 고려해야 한다.

다음 단계에서는 Slack 발송 없이 감지 결과만 기록하면서 CS 담당자의 판단과 비교해보려 한다. 놓친 상황과 불필요하게 감지한 상황을 모아 분류 기준과 임계값을 조정할 예정이다. 우선은 운영자가 실제로 확인할 만한 알림을 만드는 것부터 검증해보고 싶다.

실제 사용자 문의에서의 분류 품질과 운영 효과는 아직 확인하지 못했다.
