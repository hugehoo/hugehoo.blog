## CS가 몰리는 상황을 먼저 알아챌 수 없을까

특정 시기에 cs 문의가 급증하거나 몰린다면 특정 지점에서 문제가 발생했음을 파악할 수 있다. 문제는 이를 사람이 인지할 때 까지 시간이 걸린다는 점인데, 특정 시점에 문의가 몰릴때 어떤 내용이 많은지 알 수 있으면 이슈 대응이 더 빨라질 수 있다고 생각했다.
문의가 들어올 때마다 Slack 알림을 보낸다면 굉장히 노이지해지고 아무도 보지 않는 채널이 될 수 있다. 뮤트 처리한다 해도 결국 운영자가 다시 내용을 하나하나 읽고 취합한 후 리포팅 하기 때문에 대응이 늦어질 수도 있다. 캠페인별로 문의를 집계하고 일정 기준을 넘었을 때만 얼럿을 줄 수 있다면 문제 접근의 해상도가 높아질 것이라 예상했다.

## Jev를 이럴 때 사용하는게 맞을까?

문의 내용을 분류할 방법을 찾다가 요즘 핫하다는 Jev를 고려했다.
Jev는 텍스트 같은 비정형 입력을 받아 미리 정의한 선택지 중 하나를 고르고, 각 선택지의 확률과 confidence를 반환하는 모델이다.
[Choice 공식 문서](https://docs.typesafe.ai/primitives/choice)에도 고객 문의를 담당 부서로 분류하는 예시가 나온다.

‘보상 미지급’, ‘지급 지연’, ‘미션 미인식’처럼 유형을 정해두고 개별 cs 문의를 분류해보는 mvp를 진행했다.
mvp에서는 기존 CS 인입 경로와 Redis를 이용해 캠페인별 문의 사용자 수를 집계했다.
같은 사용자의 반복 문의는 중복으로 카운트 하지 않았고, 급증 후보가 생길 때만 최근 문의 최대 20건을 Jev로 분류해 Slack 알림을 발송하는 식으로 설계했다.
분류는 cs 문의 내용을 기준으로 정했다. ‘보상 미지급’이 많다는 결과만으로 실제 보상 처리에 장애가 있다고 확정할 수는 없다.

![CS 원본 저장 후 Redis에서 캠페인별 고유 사용자를 집계한다. 급증 기준을 넘으면 최근 최대 20건을 Jev로 분류해 Slack에 알리며, 분류 실패 시에도 문의량 알림을 보낸다.](flow.svg)

우선 이전에 인입된 실제 cs 문의를 대상으로 실제 Jev API를 호출했다.
준비한 8건 모두 기대한 유형과 일치했지만 표본 크기가 작았기 때문에 실제 cs 급증 상황에서도 정확하게 분류할 수 있는 근거로 보기 어려웠다.
주변 로직은 별도로 검증했다. 관련 테스트 174개를 통과했고, 실제 Redis에서도 중복 접수와 데이터 만료, 알림 간격 제한이 동작하는지 확인했다. 과거 문의를 늦게 처리해도 현재 문의량으로 집계하지 않는지, Jev 분류가 실패하거나 오래 걸려도 문의량 알림은 보낼 수 있는지도 테스트했다.

이 과정에서 확인한 것은 구현이 정해둔 조건대로 동작하는지였다.
문의를 얼마나 정확하게 이해하는지 알림이 운영자의 판단에 도움이 되는지는 다른 검증이 필요했다.

## 아직 부족한 부분

가장 먼저 필요한 것은 실제 문의를 대상으로 한 평가다. 사람이 문의 유형을 분류한 정답 데이터를 만들고, Jev가 어떤 유형을 자주 혼동하는지 확인해야 한다. ‘아직 지급 예정일이 지나지 않았다’는 문의와 ‘지급일이 지났는데 받지 못했다’는 문의를 잘 구분하는지도 살펴볼 필요가 있다.

표본을 고르는 방식에도 한계가 있다. 최근 20건에 특정 유형이 많다고 전체 문의에서도 같은 비중이라고 볼 수는 없다. 고정된 급증 기준 역시 평소 문의가 많은 캠페인과 적은 캠페인에 똑같이 적용해도 되는지 확인이 필요하다.

운영 측면에서는 외부로 보내는 본문에 개인정보가 남지 않는지 점검해야 하고, Redis 장애나 데이터 유실로 감지를 놓칠 가능성도 고려해야 한다.

다음 단계에서는 Slack 발송 없이 감지 결과만 기록하면서 CS 담당자의 판단과 비교해보려 한다. 놓친 상황과 불필요하게 감지한 상황을 모아 분류 기준과 임계값을 조정할 예정이다. 우선은 운영자가 실제로 확인할 만한 알림을 만드는 것부터 검증해보고 싶다.

실제 사용자 문의에서의 분류 품질과 운영 효과는 아직 확인하지 못했다.
